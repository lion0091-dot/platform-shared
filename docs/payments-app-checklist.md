# 결제 모듈 앱 필수 체크리스트 (초안) — `@platform/shared/payments`

상태: 초안(문서만, 코드·버전·태그 변경 없음). 대상: 소비 앱 개발자. 근거: 라이브러리 코드 읽기 점검과 `docs/payments-api-draft.md`. 직접 실행한 것은 모의 시험(가짜 fetch)뿐이며 실제 토스 호출은 하지 않았다. 확인 못 한 것은 「미확인」.

라이브러리는 **상태도 락도 없는 호출 래퍼**다(내부 재시도 없음). 같은 요청이 중복·동시로 들어올 때 「한 번만 반영」은 토스의 멱등키 재생과 **앱의 DB 조건부 처리**가 함께 만든다. 이 문서는 그 경계를 앱 쪽에서 점검하는 용도다.

## 1. 라이브러리가 하는 것 / 앱이 해야 하는 것
| 영역 | 라이브러리 | 앱 |
|---|---|---|
| 승인 키 | 기본 `confirm_<orderId>_<paymentKey>`(`confirmIdempotencyKey`), 형식 검증 | 재시도 때 같은 키 사용(키를 바꿔 재승인하지 않기) |
| 승인 결과 | 응답의 주문·paymentKey·금액·통화 대조, 불일치는 `approved_mismatch` | 금액은 **DB 에서 계산한 값**을 넘긴다. 화면·쿼리값을 쓰지 않는다 |
| 중복 승인 | 이미 DONE 인 재승인은 `success`(처음 승인이라는 뜻이 아님) | `UPDATE ... WHERE status <> 'PAID'` 처럼 **조건부 UPDATE, 영향 행 수 확인** 후 **처음 바뀐 요청만** 정산·재고·알림 반영 |
| 불확실 | 타임아웃·5xx·모르는 코드는 `uncertain`, 처리 중은 `processing` | `FAILED` 로 확정하지 않는다. 조회(`lookup`/`lookupByOrderId`)로 확정, 같은 키로 재시도 |
| 취소 키 | `cancelIdempotencyKey` 제공(전액 `cancel_<paymentKey>_full`, 부분은 누계+금액 포함) | **모든 취소 경로**(자동 환불·운영자 취소·불일치 후속 취소)가 이 함수로 키를 만든다. 라이브러리는 임의 키도 받으므로 앱이 강제한다 |
| 부분 취소 | 요청 직전 누계(`alreadyCanceledTotal`) 필수, 응답 누계 대조, 어긋나면 `CANCEL_*` 와 현재 누계 반환 | 누계는 **요청 직전 토스 조회값**. 취소 사유에 **요청마다 다른 값(취소 요청 ID)** 을 넣는다(같은 금액·사유의 다른 경로 취소와 구분 불가) |
| 취소 반영 | `canceled`(`alreadyCanceled` 포함) 반환 | `canceled` 와 `alreadyCanceled` 둘 다 성공 처리하되 DB 반영은 **조건부로 한 번만**(같은 금액·누계의 동시 2건은 둘 다 `canceled` 가 올 수 있다) |
| 취소 불가 | `not_cancelable` | 같은 키로 재시도하지 않고 사람 처리 |
| 면세 | 선택 인자 `expectedTaxFreeAmount` 대조 | 면세·복합과세 상점은 **서버가 DB 에서 계산해 반드시 넘긴다**(생략하면 대조하지 않는다) |
| 웹훅 | `verifyPaymentWebhook`: 본문 상태를 믿지 않고 토스를 재조회, secret 대조(`authenticated`/`refetched`/`rejected`/`lookup_failed`) | **중복 수신 제거**와 반영은 앱: 처리한 이벤트(결제+상태+거래키)를 기록하거나 조건부 UPDATE. `refetched` 는 인증됨이 아님(재조회한 payment 상태만 근거). 10초 안 200 응답 |
| 웹훅 순서 | 항상 최신 상태를 재조회하므로 순서가 뒤바뀌어도 읽기는 일관 | 오래된 이벤트가 새 상태를 덮어쓰지 않게 조건부 UPDATE(상태 전이 방향) |

## 2. 앱 점검 문장 (예/아니오로 답할 수 있게)
1. 승인 성공 처리가 `WHERE status <> 'PAID'` 류 조건부 UPDATE 이고, 영향 행 0 이면 후속 반영을 건너뛰는가?
2. 같은 주문에 승인 요청이 동시에 2건 와도 후속 반영(정산·재고·알림)이 1번인가? (로컬 DB 동시 실행 시험이 있는가)
3. 승인 금액이 DB 값인가? 면세 상점이면 `expectedTaxFreeAmount` 를 넘기는가?
4. `uncertain`·`processing` 을 실패로 확정하는 코드가 없는가? 조회 후 같은 키로 재시도하는가?
5. 모든 취소 경로가 `cancelIdempotencyKey` 로 키를 만드는가? 임의 문자열 키가 남아 있지 않은가?
6. 부분 취소의 `alreadyCanceledTotal` 이 요청 직전 토스 조회값인가? 취소 사유에 요청 ID 가 들어가는가?
7. `canceled`/`alreadyCanceled` 의 DB 반영(환불 기록·재고 복원)이 조건부로 한 번만 일어나는가?
8. `not_cancelable`·`fatal` 취소를 같은 키로 되풀이하지 않고 사람 처리로 보내는가?
9. 웹훅 중복 수신(같은 이벤트 재전송)과 순서 뒤바뀜에서 DB 가 한 번만, 올바른 방향으로만 바뀌는가?
10. 웹훅 `refetched` 결과를 「인증됨」으로 쓰지 않는가?
11. 웹훅이 몰릴 때 토스 조회(웹훅 1건당 1회)가 따라 늘어나는 것을 감안해 큐·중복 제거가 있는가?
12. 위 1·2·7·9 의 동시·중복 시험이 앱에 있는가? (공용 저장소에는 DB 가 없어 동시 시험이 없다 — 「동시 시험 없음」)

## 3. 미확인 (실호출 시험 필요)
- 멱등키 재생이 **에러 응답도** 재생하는지, 15일 이후 동작(문서가 밝히지 않아 에러도 재생된다고 가정).
- 같은 금액·같은 누계의 부분 취소 동시 2건의 실제 응답.
- 승인 직후 주문 조회·웹훅 직후 재조회의 반영 지연.
- 429 의 실제 발생과 재시도 정책.
