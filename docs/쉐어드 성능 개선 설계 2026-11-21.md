## 1. cancelPayment 직렬 토스 호출·전체 예산 옵션

**현재 상태(확인)**: `payments/client.ts` 의 `call()` 은 호출당 `TOSS_TIMEOUT_MS=15초`(상한 120초), 내부 재시도 없음. 그러나 `cancelPayment` 는 한 번의 취소 요청 뒤에 상황에 따라 **조회를 직렬로 더 호출**한다. `NOT_CANCELABLE_AMOUNT` 일 때 `findAppliedCancel`(조회 1), `already_canceled` 일 때 `getPayment`(조회 1), 부분 취소 응답의 누계가 기대와 다를 때 `checkPartialCancel`(조회 1). 최악은 취소 15초 + 조회 15초 = **30초**이고, 앱이 `cfg.timeoutMs` 를 주지 않으면 줄일 방법이 없다. 앱 함수 시간 제한(예: 10초·15초·60초 플랜별, 미확인)을 넘으면 함수가 끊겨 «결과 불명»이 된다.

**변경안**
1. `TossConfig` 에 선택 필드 `budgetMs?: number` 추가(한 공용 호출 함수 전체의 총 예산). 기본은 없음(현재 동작).
2. `call()` 은 `min(timeoutMs, 남은 예산)` 을 호출 제한으로 쓴다. 남은 예산이 0 이하이면 **추가 조회를 하지 않고** 결과를 `uncertain`(코드 `BUDGET_EXCEEDED`)으로 돌려준다. 이미 취소 POST 가 나간 뒤의 조회 생략은 기존 «네트워크 불명(uncertain)» 과 같은 의미라 호출 앱의 처리 분기가 늘지 않는다(앱은 이미 uncertain 을 조회·재호출로 복구해야 함).
3. 문서(README·payments-app-checklist): «앱 함수 한도 ≥ `budgetMs`(권장: 함수 한도 − 2초), `timeoutMs` ≤ `budgetMs`/2» 규칙과 예시. 서버리스 플랜별 한도는 앱 담당이 채운다.
4. `confirmPayment` 는 단발 호출이라 예산 옵션이 필요 없다(문서에 «단발 1회, 최대 timeoutMs» 만 명시).

**호출 앱 영향(계약 호환)**: 추가형 — 필드를 안 주면 동일. 반환형(`CancelOutcome`)에 새 kind 를 만들지 않고 기존 `uncertain` 의 `code` 값만 늘린다. 앱이 `code` 를 switch 로 닫아 놓았다면(미확인) 기본 분기 확인 필요.
**관리 포인트**: +1 옵션·+1 코드값, README 한 절.
**시험 계획**: 가짜 fetch 로 ① 예산 없음 = 기존 시험 전부 통과 ② 취소 응답이 느리고(예: 12초) 예산 14초 → 후속 조회 호출 0회·`uncertain`/`BUDGET_EXCEEDED` ③ 남은 예산이 있으면 후속 조회의 제한 시간이 남은 예산으로 줄어듦(가짜 타이머).
**우선순위**: 권장(토스 지연 시 결과 불명을 줄임, 현재 사고 사례 없음).

## 2. fcm.ts 타임아웃 (AbortSignal.timeout)

**현재 상태(확인)**: `accessToken()`(구글 OAuth)과 `sendFcm()`(FCM 발송) 의 `fetch` 에 `signal` 이 없다. 구글 쪽이 응답을 지연·무응답하면 호출한 서버 액션(wholesale 의 출고·입고 스캔 등에서 `await`, 미트 교차 리뷰 근거)이 같이 멈춘다.

**변경안**
1. 두 fetch 에 `AbortSignal.timeout(ms)` 적용. 기본 `FCM_TIMEOUT_MS = 8000`(발송 TTL 1800초와 무관), `deps.timeoutMs` 로 재정의 가능.
2. 시간 초과·네트워크 오류는 기존 `catch` 가 이미 `{ ok:false, gone:false }` 를 돌려주므로 반환형 변경 없음(토큰은 지우지 않음 — 일시 장애로 기기 토큰을 삭제하지 않는 기존 규칙 유지).
3. 호출 앱 권고(문서): 응답을 막지 않아도 되는 알림은 `after()`·fire-and-forget 으로 호출(앱 몫, 쉐어드 코드 변경 아님).

**호출 앱 영향**: 두 앱 모두 재수출만 하므로 코드 변경 없이 태그만 올리면 적용. 기본값이 생기는 것이 «동작 변경»이라 릴리스 노트에 명시.
**관리 포인트**: +1 상수·+1 deps 옵션.
**시험 계획**: 가짜 fetch 가 신호를 받고 영구 대기 → `timeoutMs` 를 짧게(예: 20ms) 주면 `{ok:false, gone:false}` 로 끝남, 토큰 요청·발송 각각, 시험 시간 증가 없음(실시간 대기 대신 짧은 타임아웃 주입).
**우선순위**: **오픈 전 필수**(출고·입고 응답 경로를 구글 지연이 막을 수 있음, 변경 작음).

## 3. fcm.ts 토큰 Promise 공유

**현재 상태(확인)**: 모듈 전역 `cached` 는 `await` 뒤에 채워지므로, 서버리스 인스턴스가 막 떴을 때 `Promise.all` 로 N개 구독에 동시에 보내면 **OAuth 토큰 요청과 RSA 서명이 N번** 나간다(인스턴스 단위, 구글 쿼터·지연 낭비).

**변경안**: 모듈 전역 `pending: { key, promise } | null` 추가. `accessToken()` 이 캐시가 없으면 진행 중 Promise 를 재사용하고, 완료(성공·실패) 시 `pending` 을 비운다. 실패(null)는 공유되되 캐시하지 않는다(다음 호출이 새로 시도). `resetFcmTokenCache()` 가 `pending` 도 비운다.

**호출 앱 영향**: 없음(내부 변경). **관리 포인트**: +1 모듈 변수.
**시험 계획**: 가짜 fetch 가 토큰 응답을 지연시키는 동안 발송 10건 동시 호출 → 토큰 요청 1회, 발송 10회. 토큰 실패 시 10건 모두 `ok:false` 이고 다음 호출은 다시 토큰 요청. 키(clientEmail·projectId) 가 다르면 공유하지 않음.
**우선순위**: 권장(2번과 같은 릴리스·같은 파일).

## 4. ai-shared-key 직렬 RPC 3회·암호문 캐시 TTL (★ 개발자 결정 사안)

**현재 상태(확인)**: AI 호출 1회가 `reservePlatformAiUsage`(RPC 1) → `withPlatformAiKey`(암호문 읽기 RPC 2 + 복호화) → AI 호출 → `recordPlatformAiUsage`(RPC 3) 의 **직렬 DB 왕복 3회**이고 암호문·복호화 키 캐시는 없다. 마스터 키 링은 호출마다 `loadKeyring`(해시 몇 번, 비용 작음). 복호화는 AES-GCM 직접 사용(KDF 없음, 비용 작음, 확인).

**변경안 후보**
- (가) **암호문 캐시 TTL 옵션** `cipherCacheTtlMs`(기본 0=끔): `withPlatformAiKey` 가 RPC 2를 TTL 동안 인스턴스 메모리에서 재사용. `markPlatformKeyInvalid`·`seal` 호출 시 즉시 비움. 최대 TTL 상한 60초 고정.
- (나) RPC 병합: `reserve` 와 `cipher` 를 한 DB 함수로 합치기 → **DB 함수·RPC 계약 변경(앱 몫 SQL)** 이라 Level 3, 설계 문서(design-ai-shared-key-module)의 계약 이름이 바뀌므로 이번 범위에서 제외(참고안으로만).

**교환(트레이드오프) — 개발자 결정 필요**
| 항목 | 캐시 끔(현재) | 캐시 켬(TTL≤60초) |
|---|---|---|
| AI 호출당 DB 왕복 | 3 | 2(캐시 적중 시) |
| 키 교체 반영 | 즉시 | 최대 TTL 지연, **서버리스 인스턴스마다 시점이 다름** |
| 키 폐기·정지(운영자 스위치) 반영 | 즉시(암호문 읽기에서 차단) | 최대 TTL 동안 폐기된 키를 계속 사용 가능(단, 회사별 예약 `reserve` 는 매 호출 DB 판정이라 회사 정지는 즉시 반영 — 설계서 기준, 최종 확인 필요) |
| 메모리 안의 복호화 키 | 호출 중에만 | TTL 동안 상주(키 노출 면 증가, 문서 «키 평문은 콜백 밖으로 나가지 않는다» 원칙과 충돌 가능) |
복호화한 키 평문을 캐시하지 않고 **암호문만** 캐시하면 노출 면은 그대로다(암호문은 DB 와 같은 수준). 위 표의 «평문 상주» 열은 평문 캐시를 선택할 때만 해당하며 본 안은 암호문 캐시만 제안한다.
**호출 앱 영향**: 추가형(미소비 상태, 확인). **관리 포인트**: +1 옵션·+1 모듈 상태·운영 문서에 «반영 지연» 한 줄.
**시험 계획**: 가짜 rpc 로 ① TTL 0 = 기존 시험 통과 ② TTL 내 2회 호출 시 암호문 RPC 1회 ③ TTL 경과 후 재조회 ④ `markPlatformKeyInvalid` 뒤 즉시 재조회 ⑤ 키·scope·provider 가 다르면 별도 캐시.
**우선순위**: **오픈 후**. 현재 AI 사용량 규모가 작아 3왕복 비용이 크지 않음(추정). 개발자가 «반영 지연 허용»을 결정하기 전에는 착수하지 않는다.

## 5. record 훅 백그라운드화

**현재 상태(확인)**: `recordPlatformAiUsage` 는 DB 기록(RPC 3) 성공 뒤 `onRecorded` 훅을 `Promise.race`(2초)로 **기다린 뒤** 반환한다. 훅은 상세 기록용이라 응답 경로에서 최대 2초를 더 쓸 수 있고, 시간 초과해도 훅 자체는 취소되지 않는다.

**변경안**: `AiSharedKeyConfig` 에 선택 필드 `scheduleHook?: (task: Promise<unknown>) => void` 추가. 주어지면 훅을 기다리지 않고 `scheduleHook(훅 실행 Promise)` 에 넘긴 뒤 `{ok:true}` 를 즉시 반환한다(앱은 `after()`·`waitUntil` 등을 연결해 응답 후 실행을 보장). 안 주면 현재 동작(2초 대기). 훅 오류는 Promise 안에서 삼키고 `hookError` 는 이 모드에서 반환값에 없다(문서화).

**호출 앱 영향**: 추가형(미소비). 앱이 `after()` 를 쓰는 Next 버전 여부는 앱 몫(미확인).
**관리 포인트**: +1 옵션. **시험 계획**: ① 미지정 = 기존 시험 통과 ② 지정 시 훅이 3초 걸려도 반환이 즉시, 전달된 Promise 가 나중에 이행 ③ 훅이 던져도 미처리 거부(unhandled rejection)가 없음.
**우선순위**: 권장(앱이 ai-shared-key 를 처음 연결할 때 함께 적용하면 부담이 작음).

## 6. package.json sideEffects

**현재 상태(확인)**: `package.json` 에 `sideEffects` 선언이 처음(2026-10-13, 5704cf7)부터 없다. 소스(.ts)를 그대로 배포하고 앱이 Next `transpilePackages` 로 빌드하므로, 번들러는 모듈 최상위 코드를 부작용 가능성으로 보수적으로 취급한다. 서브패스 `index.ts` 가 여러 모듈을 재수출하는 구조라 쓰지 않는 코드까지 번들에 남을 수 있다(실제 번들 영향은 미확인).

**변경안**: `"sideEffects": false` 추가. 전제 점검(구현 단계에서 확인): 모듈 최상위에서 전역 상태를 바꾸거나 import 만으로 동작해야 하는 코드가 없을 것. 쉐어드는 `let cached`(fcm 토큰 캐시) 같은 모듈 변수는 있지만 import 시점에 실행되는 부작용은 확인되지 않았다. 예외가 있으면 해당 파일만 배열로 지정한다.

**호출 앱 영향**: 빌드 산출물만 달라진다. 앱 빌드·시험·번들 크기 전후를 측정해야 하므로 앱 담당과 같은 날 한 번 확인(변경 없는 앱이 깨질 가능성은 낮음, 추정).
**관리 포인트**: 0(선언 한 줄). 새 모듈에 최상위 부작용을 넣지 않는다는 규칙이 +1(리뷰 체크리스트).

## 8. selectAllPages 류 공용 헬퍼 + 오류/잘림 구분 반환형

**배경**: 공통 원칙(RPC 오류를 0·«없음»으로 표시 금지, 1000행 조용히 잘림 금지). 쉐어드에는 현재 페이징·`range`·`limit` 헬퍼가 없다(확인). 오류 구분은 `ai-shared-key`(READ_FAILED 코드·`truncated` 플래그)에만 있다.

**현재 앱별 구현(확인, 묶음 A 진행 중이라 변동 가능)**
- 미트: `lib/supabase/select-all-pages.ts` — `fetchPage(from,to)` 주입, 행이 pageSize 미만이면 종료, **오류는 throw**, 전체 개수 대조 없음, 상한 없음.
- 레저코어: `lib/ledger/paging.ts` `fetchAllPages` — `count` 를 첫 페이지에서만 요청해 최종 행 수와 **대조**(일부만 읽히면 오류), 최대 50만 행 상한, 서버가 요청보다 적게 줘도 개수를 알면 계속 읽음, **오류는 throw**.
- 이음로지스: 같은 용도의 공용 헬퍼를 찾지 못함(미확인 — 이음 담당 확인 필요, 묶음 A 에서 새로 만들 수 있음).
묶음 A 결과(각 앱이 최종 확정한 헬퍼)가 나오면 아래 표의 «현재»열을 갱신한다.

**공용화 제안(안)**: 서브패스 `@platform/shared/paging`(의존성 0, 순수 함수, `fetchPage` 주입 — 쉐어드 다른 모듈과 같은 스타일). 반환형은 던지지 않는 판별 유니온:
```
type PagesResult<T> =
  | { ok: true; rows: T[]; total: number | null }
  | { ok: false; code: "READ_FAILED" | "TRUNCATED" | "TOO_MANY"; message: string; partial?: readonly T[] };
```
- 레저코어의 개수 대조·상한을 기본 동작으로, 미트의 «가장 단순한 호출 모양» 을 유지. 앱 호환용으로 `unwrapPages()`(실패 시 throw) 어댑터를 함께 제공해 기존 throw 호출부를 한 줄로 바꿀 수 있게 한다.
- 화면 쪽 규칙(문서): `ok:false` 를 0건·«없음»으로 그리지 말고 오류 표시, `TRUNCATED` 는 «일부만 표시» 경고.

**공용화 장단점**
| 기준 | 공용화함(쉐어드 신설) | 앱별 유지 |
|---|---|---|
| 중복 제거 | 두~세 구현을 하나로(헬퍼 약 30~40줄×앱 수 절감, 시험도 1벌) | 중복 유지, 구현이 갈라져 동작(개수 대조 유무, 상한, 오류 방식)이 앱마다 다름 |
| 일관성(오류/잘림 구분) | 반환형 통일로 «0건 vs 오류» 규약을 코드로 강제 | 앱마다 규약을 따로 지켜야 함, 이미 미트·레저코어가 다름 |
| 세 앱 동시 업그레이드 위험 | 신규 서브패스(추가형)라 **올리지 않은 앱은 영향 없음**. 단 앱마다 고정 버전이 달라(rc.3~rc.9) 헬퍼를 쓰려면 그 앱이 먼저 최신 태그로 올라가야 함 → 올릴 때 다른 변경(rc.4~)도 같이 들어옴 | 없음 |
| 태그·승인 절차 | 헬퍼 하나 때문에 쉐어드 push·태그 + 앱 3곳 의존성 갱신·시험·승인 필요(절차 비용이 큼) | 앱 안에서 끝남(앱 담당 승인만) |
| 장기 관리 | 버그·한도(max_rows 변경) 수정을 한 곳에서 | 앱 3곳을 각각 수정, 누락 위험 |
| 최초 구현 위험 | 앱별 요구 차이(count 사용 여부, 정렬 안정성: `order` 없이 range 로 읽으면 행 중복·누락) 정리가 선행되어야 함 | 없음 |

**권장**: **오픈 후**(결정 대기). 지금은 묶음 A 에서 각 앱이 정확성(오류·잘림) 문제를 앱 헬퍼로 먼저 고치고, 세 앱이 «같은 계약(개수 대조·상한·오류 코드)»으로 수렴한 것이 확인되면 그 계약대로 공용화한다. 수렴 전에 공용화하면 세 앱이 동시에 맞춰야 하는 부담만 생긴다. 공용화 시 정렬 안정성(`order` 필수 인자 또는 검사)을 계약에 넣는다(미확인: 앱별 호출부의 정렬 지정 여부).
**시험 계획(공용화할 경우)**: 미트·레저코어 헬퍼의 기존 시험 사례를 그대로 이식해 동치성 확인 + ① 서버가 1000행에서 조용히 자름(count 로 감지 → `TRUNCATED`) ② 오류 → `READ_FAILED`(0건 아님) ③ 상한 초과 → `TOO_MANY` ④ 빈 결과는 `ok:true, rows:[]`.
**관리 포인트**: +1 서브패스(+약 60줄·시험), 앱별 중복 −2~3 개.
