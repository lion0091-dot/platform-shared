# 테넌트 비밀 저장·암호화 통일 설계안 (개정 4판, 2026-10-18)

상태: **설계안 — 코드·마이그레이션·커밋·push·태그 없음.** 대장 경유 사장님 승인(Go)으로 작성.
개정 이력: 1판(봉투·키 형식 통일) → 2판: **앱 B 도 앱 A 처럼 전용 비밀 표로 옮긴다**(사장님 결정 2) → 3판: **공개 클라이언트 키·provider 는 테넌트 소유 표에 두고 시크릿만 전용 표로**, 그리고 **앱 A 도 같은 방식으로 맞춘다**(사장님 결정 9 확정 — 두 앱 완전 동일 구조). → 4판: 사장님 결정 4·5·10·11·12 확정 + **접속 기록을 두 앱이 같은 방식으로 맞춘다**(5-5A). 앱 A·앱 B 모두 DB 변경을 포함하므로 **Level 3 — 구현은 설계 확정 후 별도 승인.**
범위: 소비 앱 두 곳이 테넌트(운영사/공급사)의 **토스 결제 키**와 **알림톡 자격정보**를 저장·암호화하는 방식을 하나로 맞춘다.
공개 저장소 문서이므로 비공개 앱의 이름·파일 경로·줄 번호·마이그레이션 번호는 쓰지 않는다(앱 A / 앱 B). 앱별 상세는 각 앱 담당의 문서를 본다.
표시: **[확인]** = 코드·마이그레이션을 직접 읽어 확인, **[미확인]** = 추정·실측 필요.

원칙(변경 없음): 테넌트가 자기 계약·키를 쓰고 돈은 플랫폼을 거치지 않는다. 비밀번호·키는 응답·로그·오류 문구에 나오지 않는다. 키가 없거나 읽지 못하면 fail-closed(평문 폴백 금지).

## 2. 공용 봉투 형식 (1판 유지)

### 2-1. 이름: `ENC:v2`
앱 A 의 기존 암호문이 이미 `ENC:v1:`(AAD=테넌트 id 만)이므로, AAD 를 "테넌트+provider"로 바꾼 새 형식을 같은 접두로 쓰면 구분이 안 된다. 기존 `ENC:v1:` 은 읽기 전용 레거시, 새 형식은 `ENC:v2:`. → **결정 1: 확정(사장님)**.

### 2-2. 형식
```
ENC:v2:<kid>:<base64url( iv(12) ‖ 태그(16) ‖ 암호문 )>
```
- AES-256-GCM, iv 는 매번 `randomBytes(12)`.
- **AAD** = UTF-8 `"platform-secret/v2|" + tenantId + "|" + provider`. tenantId 는 소문자 uuid, provider 는 `^[a-z0-9-]+$` 허용 목록 슬러그(`toss`·`bizppurio`·`popbill` …). 앱 B 는 공급사 id 가 tenantId.
  - 다른 테넌트 행·같은 테넌트의 다른 provider 칸으로 옮긴 암호문은 복호화 실패.
- **kid** = 마스터 키 바이트 SHA-256 앞 4바이트 hex(8자). 설정 불필요, 키 값 비노출.
- 평문은 provider 별 **JSON 한 묶음**(필드 단위가 아니라 묶음 단위 교체·검증). 모듈은 문자열만 다루고 JSON 구조는 호출 쪽이 정한다.
- 길이는 기존 저장 제약(20~4000자) 안.

### 2-3. 읽기 전용 레거시 (이전 기간에만)
| 형식 | 식별 | 복호화 | 반환 |
|---|---|---|---|
| 앱 A 기존 | 접두 `ENC:v1:` | AAD=테넌트 id | `needsRewrite: true` |
| 앱 B 기존 | 접두 없음, 점 2개로 3분할 | AAD 없음 | `needsRewrite: true` |
| 공용 v2 | 접두 `ENC:v2:` | AAD=테넌트+provider | 현재 키면 `false`, 이전 키면 `true` |

레거시 **쓰기**는 제공하지 않는다. 단 앱 B 롤백 스크립트(5-6절)만 레거시 쓰기 함수를 쓴다(스크립트 안에 두고 공용 API 로는 공개하지 않는다).

### 2-4. 키 형식 호환
`^[0-9a-fA-F]{64}$` → hex 32바이트, 그 외 → base64(표준·url-safe) 디코드 후 정확히 32바이트, 아니면 `SECRET_KEY_INVALID`. 두 형식은 길이가 달라 모호하지 않다. **각 앱은 지금 환경변수 값을 그대로 쓴다 — 이전 때 키를 바꾸지 않는다**(키 교체와 형식·구조 이전을 분리).

## 3. 키 로더와 로테이션 (1판 유지)

```ts
// 서브패스 export: "@platform/shared/secrets" (node:crypto → 서버 전용) — P1 로컬 구현 완료(src/secrets)
loadKeyring(env, opts?): Keyring
  // opts.current  = 현재 키 환경변수 이름 (앱 A: TENANT_SECRET_KEY, 앱 B: CREDENTIAL_ENCRYPTION_KEY)
  // opts.previous = 이전 키들 환경변수 이름(쉼표 다수 허용, 기본 "<current>_PREVIOUS")
  // 오류: SECRET_KEY_MISSING / SECRET_KEY_INVALID / SECRET_KEY_DUPLICATE
  // Keyring: currentKid, previousKids 만 노출(키 바이트 비노출, JSON·콘솔 출력도 kid 만)
sealSecret(plain, { tenantId, provider }, ring): string                                // 항상 ENC:v2, 현재 키
openSecret(token, { tenantId, provider }, ring): { plain, needsRewrite, format }       // format: "v2" | "v1" | "legacy-dotted"
  // 오류: SECRET_CONTEXT_INVALID / SECRET_FORMAT / SECRET_KEY_UNKNOWN / SECRET_DECRYPT_FAILED
resolveSecret(stored, ctx, keyring | () => keyring, parse): SecretState<T>             // 3상태 보조(결정 8)
  // { state:"ok", value, needsRewrite, format } | { state:"absent" } | { state:"unavailable", reason }
  // reason: SecretErrorCode | "READ_FAILED" | "INVALID_PAYLOAD"  (코드만, 값·키 조각 없음)
readFailed(), jsonSecret(validate)                                                      // DB 읽기 실패 상태 / JSON 평문 파서 도우미
```
- 컨텍스트 검증: `tenantId` `^[A-Za-z0-9-]{1,64}$`(v2 에서 소문자 정규화), `provider` `^[a-z0-9-]{1,32}$`. provider 허용 목록은 모듈이 아니라 각 앱의 DB 제약이 관리한다(형식만 검사).
- 레거시 이름: `v1`(기존 `ENC:v1:`, AAD=테넌트 id 문자열 그대로·provider 미묶음), `legacy-dotted`(접두 없음 `iv.태그.암호문`, AAD 없음). 레거시는 읽기만, 쓰기 경로 없음.
- 오류는 코드 문자열만(값·암호문·키 조각 없음). 환경 객체를 인자로 받는다.
- 현재 키 = 쓰기·우선 읽기, `_PREVIOUS` = 읽기 전용. 복호화는 kid 로 키 선택, 키링에 없으면 `SECRET_KEY_UNKNOWN`(분실·환경 혼동과 변조를 구분). 레거시는 현재 키 → 이전 키 순으로 시도.
- 로테이션 절차(무중단): 새 키를 현재로, 옛 키를 `_PREVIOUS` 로 → 배포 → 재암호화 스크립트(`needsRewrite` 행) → 남은 구키 행 0건 확인 → `_PREVIOUS` 제거.
- 키 값은 **앱·환경별로 다르게**(앱 A ≠ 앱 B, 리허설 ≠ 스테이징 ≠ 운영). 키 백업 보관은 [미확인], 결정 5.
- 읽기 결과를 3상태(ok / absent / unavailable)로 매핑하는 얇은 보조(앱 A 가 세 곳에서 각자 구현)는 공용으로 포함(결정 8=(b) 확정).

## 4. 공용 vs 앱별

### 4-1. platform-shared (서브패스 `secrets`, 의존성은 `node:crypto` 뿐)
봉투(2절), 레거시 읽기 2종, 키 로더·키링, 오류 코드, 입력 검증, (결정 8 시) 3상태 보조, **시험 벡터**(`account` 의 `__vectors__` 방식, TEST-ONLY 가짜 키로 만든 v2·두 레거시 고정 암호문 + 다른 테넌트/다른 provider/변조/없는 kid 거절). 공개 저장소이므로 실제 키·암호문은 넣지 않는다.

### 4-2. 앱별로 남김
DB 접근(표/RPC), 권한·접속 기록·설정 화면·상태 응답(암호문 비반환), 키 교체 가드(진행 중 결제 거절 등 결제 도메인 규칙), 토스 키 형식 정책·저장 전 인증 확인, 알림톡 대행사별 필드 검증, 환경변수 이름.

## 5. 앱 B 전용 비밀 표 설계 (신규)

목표: 앱 A 의 전용 비밀 표와 **같은 모양·같은 권한 모델**. 공급사 = 테넌트.

### 5-1. 표
```
전용 비밀 표            -- 앱 A 의 기존 비밀 표와 같은 모양. 앱 B 에서는 FK 대상이 공급사 표
  tenant_id   uuid  not null  references <공급사 표>(id)     -- 공급사 id (= AAD 의 tenantId)
  provider    text  not null  check (provider in ('toss','bizppurio'))
  ciphertext  text  not null  check (length(ciphertext) between 20 and 4000)
  updated_by  uuid  references auth.users(id) on delete set null   -- 앱 B 의 기존 변경 이력도 같은 참조를 씀 [확인]
  updated_at  timestamptz not null default now()
  primary key (tenant_id, provider)
```
- 이름을 앱 A 와 같게 하는 것을 권장(운영 문서·시험 벡터·점검 쿼리를 공유). 앱 B 어휘에 맞춰 다른 이름·열 이름을 쓰는 것도 가능(사소한 선택; 권장은 같은 이름).
- `on delete` 는 지정하지 않는다(공급사 행은 탈퇴 후에도 익명화만 되고 삭제되지 않음 [확인: 파기 함수가 UPDATE 로 비움]). 비밀 행 삭제는 명시적으로(5-5, 6-4).
- provider 허용 목록은 CHECK 제약(앱 A 와 같음; provider 추가마다 마이그 필요 — 둘 다 같은 한계).
- **변경 이력 트리거를 이 표에 붙이지 않는다**: 앱 B 의 변경 이력 트리거는 행 전체를 JSON 으로 복사하므로 붙이면 암호문이 이력 표에 복제된다.

### 5-2. RLS·권한
- `enable row level security`, 정책 없음, `revoke all ... from anon, authenticated` (기본 권한이 열려 있어도 명시 회수), `grant all ... to service_role`.
- 공급사 표의 컬럼 단위 SELECT 허용 목록은 **그대로 둔다**: 새 표는 별개 표라 기존 허용 목록과 무관하고, 옛 비밀 컬럼은 이미 허용 목록 밖이다. 옛 컬럼을 지워도 회수할 권한이 없다(컬럼이 사라지면 권한도 사라짐). 주의: 그 마이그레이션이 허용 목록을 "실행 시점 컬럼"으로 계산했으므로, 새로 공급사 표에 컬럼을 더할 때 GRANT 규칙은 그대로 유효하다.

### 5-3. RPC (앱 A 와 같은 모양, SECURITY DEFINER, `search_path=public, pg_temp`)
| RPC | 호출자 | 동작 |
|---|---|---|
| `secret_save(p_tenant, p_provider, p_cipher)` | authenticated | 호출자가 해당 공급사의 owner·manager(또는 현행처럼 슈퍼관리자)인지 DB 안에서 검사(기존 "공급사 직원 여부+역할" 함수 재사용 [확인: 존재]), 길이·provider 검증, upsert, 접속 기록 한 줄(값 없음). 토스일 때는 같은 트랜잭션에서 공급사 표의 공개 값(5-4)도 갱신 |
| `secret_remove(p_tenant, p_provider)` | authenticated | 같은 권한 검사, 행 삭제, 토스일 때 공개 값 비움, 접속 기록 |
| `secret_status(p_tenant)` | authenticated | provider 별 configured·updated_at (암호문 비반환) |
| `secret_cipher(p_tenant, p_provider)` | **service_role 만** | 암호문 반환(결제 승인·웹훅·크론처럼 사용자 세션이 없는 경로용). 복호화는 앱 서버 |

- 현재의 "앱이 역할 확인 후 service_role 로 직접 읽고 씀" 방식 대신 DB 안에서도 역할을 검사하는 이유: 앱 B 에서 과거 "역할 제한이 화면에서만 지켜져 API 직접 호출로 읽히던" 결함이 있었다 [확인: 컬럼 권한 회수 마이그의 머리말]. 앱 코드의 역할 검사는 첫 관문으로 남긴다.
- 대안(최소 변경): RPC 없이 서버 도우미가 새 표를 service_role 로 직접 접근(지금 방식 유지). DB 변경이 적은 대신 앱 A 와 모양이 달라진다 — 결정 10.
- [확인: 앱 B 담당] 한 사용자는 조직 하나(직원 표 사용자 UNIQUE, 조직↔공급사 1:1)라 `p_tenant` 는 호출자 조직의 공급사 하나로 확정된다. 현재 **슈퍼관리자 대행 저장 경로는 없다**(저장 액션이 조직 소속 공급사 id 를 요구하고, 조직 소속이 없는 슈퍼관리자는 id 가 null) → RPC 에 슈퍼관리자 예외를 넣지 않는다(필요성은 사장님 결정 사항이 아님: 현행 유지).

### 5-4. 무엇이 표로 가고 무엇이 공급사 표에 남는가
| 값 | 이동 | 이유 |
|---|---|---|
| PG 시크릿 키 | **표(provider=`toss`)**, 묶음 `{secretKey}` | 비밀 |
| PG 클라이언트 키·공급자 | **공급사 표에 유지**(권장) | 브라우저 위젯에 그대로 노출되는 공개 값이고, 비로그인 상점·결제·고객·관리자 화면의 **다수 경로가 세션으로 직접 읽음**. 암호문 안에 넣으면 공개 페이지마다 서버가 복호화해야 하고 읽기 경로 전부를 다시 짜야 한다 |
| 알림톡 공급자·계정·비밀번호·발신키·발신번호·템플릿 코드 | **표(provider=`bizppurio`)**, 묶음 전체 | 결정 3: 앱 A 방식 |
| 알림톡 폴백 on/off | 공급사 표에 유지 | 비밀이 아닌 설정값 |
| 팝빌 연동 식별자 | 이번 범위 밖 | 비밀 아님(연동 ID), 별도 |

- **결정 9 확정 (사장님 2026-10-18)**: 공개 클라이언트 키·provider 는 **테넌트 소유 표**에 두고 시크릿만 전용 표로 간다. **앱 A 도 같은 방식으로 맞춘다**(6A). 두 앱이 같은 구조: 테넌트 표의 결제 공급자·공개 클라이언트 키 열 열 + 전용 표의 `toss` 행(`{secretKey}`).
- 두 값이 어긋나지 않게 **저장·삭제 RPC 가 같은 트랜잭션에서 둘을 함께 갱신**한다 — 규칙은 6C.
- 알림톡 발송 경로의 "설정돼 있나" 확인은 복호화 없이 `secret_status`(또는 service_role 의 존재 조회)로 한다.

### 5-5. 접속 기록
앱 B 는 기존 접속 기록 표를 재사용한다(사장님 결정 10). 앱 A 도 같은 방식으로 맞춘다 — 기록 대상·규칙·함수 인터페이스는 **5-5A** 에 정리했다.

### 5-5A. 접속 기록 통일 (4판 신규)

사장님 지시: 기록 대상은 **키 저장·삭제·변경(값 제외)만**. 복호화 읽기·상태 조회는 기록하지 않는다(결제·주문 경로에 쓰기 금지, 성능). 두 앱이 같은 방식으로 맞춘다.

#### 현황 비교 [확인: 코드, 앱 A 담당 답변은 부록 4]
| | 앱 A | 앱 B |
|---|---|---|
| 기존 표 | 앱 A 의 관리자 접근 기록 표 — **관리자 개인정보 접근·변경 기록**. 열: 관리자 id, action, target_type, target_id, detail(jsonb), 테넌트 id(후속 추가), 시각. 수정·삭제 금지 트리거. 관리자 RPC 전반(정산·장부·기사 등급·세금계산서 등)이 같은 표를 씀 | 앱 B 의 접속 기록 표 — **로그인·접속 이벤트**. 열: 사용자 id, 이벤트 이름(≤60자), IP, UA, 시각. 슈퍼관리자만 조회, 2년 보관·정리 함수 |
| 키 저장·삭제 기록 | 현재 저장 RPC 가 남기는 기록 이름은 기존 키 저장 기록 이름 3종(결제·알림톡(로컬 미적용)·세금계산서(팝빌, 상세 비어 있음)) 로 남김, 토스·알림톡은 detail `{op: save|remove}` | 없음(새로 도입) |
| 보관 | 수정·삭제 불가라 정리 정책 없음(미확인: 별도 정리 계획) | 2년 후 정리 |
| 테넌트 식별 | 열 있음 | 열 없음(사용자→조직→공급사 1:1 로 추적 가능 [확인]) |

두 표는 **목적과 모양이 다르다**(앱 A = 관리자 행위 기록, 앱 B = 접속 이벤트 기록). 둘 다 이미 "누가 언제 무엇을 했다"를 값 없이 남기는 용도다.

#### 안 비교
| | 안 1: **기존 표 유지 + 기록 항목·규칙·함수 인터페이스 통일** (권장) | 안 2: 두 앱에 **같은 모양의 새 전용 표**(`secret_events`) | 안 3: 접속 기록을 **공용 표 하나로 통합** |
|---|---|---|---|
| 내용 | 각 앱의 기존 표에 쓰되, 기록하는 항목·이벤트 어휘·호출 함수 모양을 같게 | 비밀 이벤트만 담는 새 표를 두 앱에 같은 열로 신설 | 앱 A 앱 A 의 관리자 접근 기록 표·앱 B 앱 B 의 접속 기록 표 를 한 모양으로 합치고 기존 기록 호출을 모두 이전 |
| DB 변경 | 앱 A: 없음(기존 표). 앱 B: 없음(기존 표) | 두 앱 모두 표 신설 | 두 앱 모두 대규모(기존 호출 수십 곳 이전) |
| 앱 A 영향 | 키 RPC 의 action 이름만 통일(과거 행은 옛 이름 그대로) | 키 RPC 가 새 표로 이동, 과거 행은 옛 표에 남음 | 관리자 RPC 전반 수정 |
| 앱 B 영향 | 키 RPC 가 기존 표에 한 줄 기록 | 키 RPC 가 새 표에 기록 | 로그인 이벤트 기록 경로 수정 |
| 조회 | 기존 조회 수단 그대로(앱 B: 슈퍼관리자 / 앱 A: 관리자 기록 조회) | 새 표 조회 수단 필요 | 통합 조회 |
| 장점 | 변경 최소, 위험 최소, 사장님 지시("앱 B와 동일한 방식")를 항목·규칙으로 충족 | 두 앱이 완전히 같은 표 모양, 비밀 이벤트만 따로 조회 쉬움 | 완전 통일 |
| 단점 | 표 모양은 앱마다 다름(앱 B 에 테넌트 열 없음) | DB 구조 추가 2건(Level 3), 기존 기록 표와 이중화 | 범위 과대, 이번 목적(비밀 통일) 밖, 위험 큼 |

**권장: 안 1.** 사장님 지시의 핵심(무엇을 기록하고 무엇을 기록하지 않는가)은 표 모양이 아니라 **규칙**이므로 규칙·어휘·함수 인터페이스를 통일하면 충족된다. 표를 새로 만드는 안 2 는 "비밀 이벤트 전용 조회"가 필요해질 때 후속으로 검토한다.

#### 통일 규칙 (안 1)
1. **기록하는 것**: 비밀의 **저장(최초)·변경(기존 값 교체)·삭제** 세 가지, provider 단위(토스·알림톡·팝빌). **값·암호문·키 조각은 기록하지 않는다.**
2. **기록하지 않는 것**: 복호화 읽기(서버가 키를 읽는 순간), 상태 조회, 존재 확인, 결제·주문·알림 발송·크론·웹훅 경로 전부. 이 경로들은 읽기만 하며 쓰기를 추가하지 않는다(성능·잠금 경합 방지).
3. **기록 시점**: 저장·삭제 RPC 안에서 6C 순서의 마지막 단계로, **같은 트랜잭션**. 저장이 롤백되면 기록도 없다(기록만 남고 저장은 실패한 상태가 생기지 않음).
4. **이벤트 어휘** (두 앱 공통): `SECRET_SAVE`(최초), `SECRET_REPLACE`(기존 교체), `SECRET_REMOVE`(삭제). 최초/교체 구분은 RPC 가 upsert 전에 행 존재를 보고 결정.
5. **필드**: 누가(사용자 id), 언제, 어느 테넌트, 어느 provider, 어떤 이벤트.
   - 앱 A: `action` = 이벤트, `target_type` = `tenant_secret`, `target_id` = provider, `detail` = `{}`(비워 둠 또는 provider 중복 없음), 테넌트 열 = 테넌트 id.
   - 앱 B: `event` = `secret_save:toss` 형태(소문자, ≤60자 — 최장 `secret_replace:bizppurio` 는 24자), 사용자 id = 호출자. 테넌트는 사용자→조직 1:1 로 추적한다. 테넌트를 직접 조회해야 한다면 접속 기록 표에 **nullable 열 추가**(결정 15)로 해결 가능하나 이번에는 추가하지 않는다.
6. **함수 인터페이스** (두 앱 DB 안에서 동일한 이름·인자): `record_secret_event(p_tenant uuid, p_provider text, p_event text)` — 저장·삭제 RPC 내부에서만 호출하는 SECURITY DEFINER 도우미, 클라이언트 execute 회수. 각 앱이 자기 기존 표에 쓰는 한 줄을 캡슐화하므로 표 모양 차이는 이 함수 안에 숨는다. 앱 코드는 이 함수를 직접 부르지 않는다.
7. **기존 앱 A action 이름**: 기존 키 저장 기록 이름 3종(결제·알림톡·세금계산서) 는 새 어휘로 바꾼다. 과거 행은 옛 이름으로 남는다(수정 금지) → 조회·점검은 **두 이름을 모두** 본다. 팝빌(기존 세금계산서 키 저장 기록 이름)은 이번 토스·알림톡 범위 밖이므로 **함께 맞출지 선택**(권장: 함께 — 같은 RPC 모양이면 한 번에 정리).
8. **시험**: ①저장 시 기록 1건·값 미포함 ②롤백되는 저장은 기록 없음 ③삭제 기록 ④**읽기 RPC·상태 RPC·암호문 조회 RPC 는 기록을 만들지 않음** ⑤클라이언트 직접 호출로 `record_secret_event` 실행 불가.
9. **보관**: 앱 B 는 기존 2년 정리 정책을 따른다. 앱 A 는 수정 금지 표라 정리 정책 없음 — 값이 없는 행위 기록이라 민감도는 낮으나, 보관 기간 정책은 별도 사안(이 설계 범위 밖, 법무 확인 항목).

#### 변경 범위 (접속 기록)
앱 A: 후속 마이그에 도우미 함수 1개 + 키 RPC 3~4개 수정(공개 키 분리 마이그와 같은 묶음). 앱 B: 새 표 마이그에 도우미 함수 1개 포함. DB 구조 추가 없음(안 1).

### 5-6. 탈퇴 파기 연동 (필수)
- 파기 함수는 비밀 컬럼을 NULL 로 만든다. 이전 후에는 **새 표 행을 삭제**해야 한다. 함수를 `create or replace` 로 재정의하되, **최신 정의를 복사해 수정**한다(여러 마이그레이션이 같은 함수를 재정의해 왔다 [확인]; 옛 정의를 복사하면 이후 추가된 파기 항목이 되돌려진다).
- 단계별: ① 표 신설 마이그레이션에서 전용 비밀 표에서 대상 테넌트 행을 삭제하는 처리를 **추가**하고 옛 컬럼 NULL 처리는 유지(이중 기간) ② 옛 컬럼 삭제 마이그레이션에서 **같은 마이그레이션 안에** 옛 컬럼 참조를 제거(plpgsql 은 생성 시 컬럼 존재를 검사하지 않아, 컬럼만 지우면 파기 크론이 **런타임에 조용히 실패**한다).
- 함수의 "이미 비운 행은 건너뜀" 조건이 옛 비밀 컬럼의 NULL 여부를 쓴다 → 새 표 존재 조건으로 교체.
- 파기 시험 스크립트와 개인정보 유출 대응 문서·이관 설계 문서의 컬럼 언급도 갱신 대상.
- 범위 밖 관찰: 비밀은 탈퇴 후 보관 기간(5년) 경과까지 남는다(현행 동일). 탈퇴 즉시 비밀만 삭제하는 것은 선택 개선.

## 6. 앱 B 기존 값 → 새 표 이전 절차

핵심: **표 신설(추가만) → 이중 읽기 → 백필(복사, 옛 값 유지) → 관찰 → 옛 컬럼 비우기 → 옛 컬럼 삭제.** 파괴적 단계(비우기·삭제)는 맨 끝에 두고, 그 전까지는 코드·데이터 롤백이 모두 가능하다. 환경 순서: **리허설 → 스테이징 → 운영**, 각 환경·각 단계 사장님 승인.

### 6-1. 단계
| 단계 | 내용 | 파괴성 | 롤백 |
|---|---|---|---|
| M1 | 마이그레이션: 표·RLS·RPC·파기 함수(새 표 삭제 추가, 옛 컬럼 NULL 유지) 추가 | 없음(추가만, `if not exists`) | 표·함수 drop 스크립트(작성해 둠). 빈 표라 데이터 손실 없음 |
| A1 | 앱 배포: **읽기 = 새 표 우선, 없으면 옛 컬럼(레거시 복호화)**, 쓰기 = 새 표(v2) | 없음 | 이전 앱 버전으로. 단 A1 이후 **새 표에만 저장된 키**는 이전 앱이 못 읽음 → 해당 공급사 재입력(허용 가능한지 결정 11) |
| B1 | 백필 스크립트: 옛 컬럼에 값이 있고 새 표에 행이 없는 공급사마다 복호화 → 묶음 생성 → v2 봉인 → `insert ... on conflict do nothing` → 열어서 원문 일치 검증. **옛 컬럼은 건드리지 않음** | 없음(복사) | 새 표 행 삭제(스크립트 `--undo`) |
| V1 | 검증: 옛 값 있는 공급사 수 = 새 표 행 수, 표본 복호화, 리허설은 토스 테스트 키로 실제 승인 조회, 알림톡은 [미확인: 안전한 시험 방법] | 없음 | — |
| O1 | 관찰 기간(운영 권장 2~4주): 읽기 경로의 "옛 컬럼 폴백 사용" 횟수 계수(값 없이 건수만) → 0 확인 | 없음 | — |
| C1 | **옛 비밀 컬럼 NULL 처리**(스크립트, 대상: 새 표에 행이 있는 공급사만) | **파괴적(데이터 삭제 — Level 3)**, 선행: DB 백업·시점 복구 가능 여부 확인 [미확인] | 역방향 스크립트(`--to-legacy`: 새 표 → 옛 컬럼, 레거시 형식 쓰기). 마스터 키가 같아 원문 복원 가능 |
| F1 | 앱 배포: 폴백 코드 제거(새 표만 읽음), 폴백 계수 코드 제거 | 없음 | 이전 앱 버전 (C1 전이면 옛 값 있음, C1 후면 역방향 스크립트 먼저) |
| D1 | 마이그레이션: 옛 비밀 컬럼 삭제 + **같은 마이그레이션에서 파기 함수·관련 시험·타입 생성물 정리** | **파괴적(스키마)** | 컬럼 재추가 마이그레이션(빈 상태) + 역방향 스크립트. 사실상 D1 이후 롤백은 복원 작업 |

- 시간 여유가 있다는 방침에 맞춰 C1·D1 은 **운영에서 가장 늦게** 하고, 리허설·스테이징에서 전 단계를 한 번씩 완주(역방향 포함)한 뒤 운영 착수.
- 리허설은 암호화 컬럼을 비워 두는 기본 방침이고(공급사 0, 암호화 키 환경변수도 없음 [확인: 앱 B 담당]) 따라서 **리허설 전용 키 설정 + 시험 행 심기**를 허용해야 이전 시험이 된다 — 결정 7.
- 스테이징의 기존 값은 PG 시크릿 1건(토스 테스트 키, 시험 데이터)·알림톡 비밀번호 0건 [확인: 건수만]. 이 1건은 백필 대신 **재입력이 더 쉽다**(이전 절차 시험은 별도 시험 행으로).

### 6-2. 이중 읽기 기간의 쓰기·삭제 규칙 (버그 방지)
- **삭제**: 비밀 삭제 시 새 표 행과 옛 컬럼을 **둘 다** 지운다(폴백이 삭제한 키를 되살리면 안 된다).
- **빈 값 저장**: 기존 동작("시크릿 키를 비워 저장하면 기존 값 유지")은 기존 값이 옛 컬럼에만 있어도 유지되어야 한다 → 저장 시 새 표에 없으면 옛 값을 복사 후 갱신.
- **부분 저장**: 알림톡은 묶음 교체이므로, 비밀번호만 비워 저장하는 UI가 있으면 기존 묶음을 읽어 병합하는 경로가 필요(앱 A 와 동일 규칙) [확인: 앱 B 담당] 알림톡 저장은 비밀번호가 빈 문자열이면 기존 암호문을 유지하고 나머지 필드는 매번 덮어쓴다 → 묶음 암호문으로 바뀌면 **기존 묶음을 읽어 병합**해야 한다(PG 시크릿 키도 비우면 기존 유지).
- 백필과 사용자 저장의 경합: 백필은 `on conflict do nothing`(사용자 저장이 이긴다).

### 6-3. 백필·비우기·역방향 스크립트 요구사항
- 서버 일회성 스크립트(service_role), **기본 드라이런**(건수·형식별 분포만), 실행은 명시 플래그, 멱등.
- 출력·로그에 평문·암호문·키 없음. 건수 요약(총/이전/건너뜀/실패)과 공급사 id·오류 코드만.
- 행 단위 검증(왕복 일치) 후 반영, 실패 행은 건너뛰고 보고(전체 중단 안 함).
- 비우기(C1)는 **새 표 행이 존재하고 열린 경우에만** 해당 공급사의 옛 컬럼을 비운다(`where` 로 재확인).
- 역방향은 같은 구조, 레거시 형식 쓰기.

### 6-4. 코드 경로 영향 [확인: 호출 지점 검색]
| 영역 | 영향 |
|---|---|
| 설정 저장 2종(PG, 알림톡) | 암호화 호출·저장 위치 교체(RPC), 기존 값 유지 규칙(6-2) |

### 알림톡 (앱 A 로컬 커밋) 영향
- **지금 형식은 변경 필요 없음.** 알림톡은 계정·비밀번호·발신키·발신번호·템플릿 코드가 모두 암호문 안(provider `bizppurio`)이고, 이는 **결정 3(묶음 전체를 한 암호문)** 과 일치한다. 결정 9 는 "공개 클라이언트 키·provider"에 관한 것이므로 알림톡에는 적용하지 않는다(결정 12 권고).
- 이유: 알림톡에는 공개 화면에서 읽는 값이 없다(분리의 이득인 "공개 경로에서 시크릿 복호화 회피"가 해당 없음). 계정·발신키는 대행사 과금·발신 권한과 연결될 수 있어 [미확인] 암호문 안에 두는 편이 안전하다. 분리하면 RPC 4개·화면·시험이 다시 바뀌는 비용만 든다.
- 영향은 **시그니처**뿐: 기존 암복호화 함수 → `sealSecret/openSecret`(provider=`bizppurio`). 알림톡 마이그와 코드는 아직 어디에도 적용·push 되지 않았으므로(로컬 전용) 처음부터 v2 로 시작하면 **이전 비용이 없다**(저장된 v1 알림톡 암호문이 존재한 적 없음). DB 는 암호문 문자열만 보므로 이 마이그는 봉투 형식과 무관해 **수정 불필요**.
- 알림톡을 분리하는 쪽으로 결정이 나면(결정 12 반대): 비밀번호만 시크릿으로 남기고 나머지는 테넌트 소유 표로 옮기며 알림톡 RPC·읽기 모듈·설정 액션·화면·시험을 수정한다. 데이터가 없어 이전 비용은 없다. 미적용 로컬 마이그를 고치면 로컬 롤백→재적용 시험을 다시 해야 한다.

## 6C. 저장 RPC 규칙 — 공개 키 갱신과 시크릿 저장은 한 트랜잭션

적용 대상: 두 앱의 토스 저장·삭제·상태 RPC. (단일 SQL 함수 본문은 하나의 트랜잭션이므로 중간 실패는 전체 롤백된다.)

**저장 `(공개 키, 암호문, 앱별 가드 인자)`** — 순서 고정:
1. 호출자 역할 검사(앱 A: 대표만 / 앱 B: owner·manager), 기능 스위치(앱 A 결제 기능 스위치) 확인.
2. 공개 키 형식 검증(DB 안, 예: `^(test|live)_ck_[A-Za-z0-9_\-=]{8,120}$`), 암호문 길이 검증(20~4000), provider 허용 목록.
3. 앱별 교체 가드(앱 A: 진행 중 결제 거절, 환불 가능 승인 결제는 확인 필요. 앱 B: [미확인] 가드 유무).
4. 시크릿 행 upsert(`updated_by`, `updated_at`).
5. 테넌트 소유 표의 결제 공급자·공개 클라이언트 키 열 갱신.
6. 접속 기록 한 줄(값 없음).
→ 4·5 중 하나라도 실패하면 전부 롤백. 앱 코드에서 두 번에 나눠 호출하지 않는다.

**삭제**: 시크릿 행 삭제 + 공개 열 NULL + 접속 기록, 같은 교체 가드(진행 중 결제 거절 등). 앱 B 는 이중 읽기 기간에 옛 컬럼도 함께(6-2).

**암호문을 비워 저장(시크릿 유지, 공개 키만 변경)**: 허용하려면 새 공개 키의 모드(`test`/`live`)가 **기존 공개 키의 모드와 같을 때만** 허용(DB 가 접두로 검사). 모드가 바뀌면 시크릿도 새로 받아야 한다(시크릿을 복호화할 수 없는 DB 가 짝을 확인하지 못하므로).

**상태 `()`**: `configured`(= 시크릿 행 존재 **그리고** 공개 열 NOT NULL), 공개 키(표시용), 모드(공개 키 접두), `updated_at`, 교체를 막거나 경고할 결제 건수. 암호문은 반환하지 않는다.

**불변식**: 공개 클라이언트 키 열이 NOT NULL 이면 토스 시크릿 행이 존재하고, 그 역도 성립. DB 제약으로 걸 수 없는 교차 표 조건이므로 ①공개 열은 RPC 로만 변경(앱 A 의 테넌트 표는 클라이언트 전면 회수, 앱 B 는 service_role 만 쓰기 — 서버 코드에서 공개 열 직접 UPDATE 금지) ②읽는 쪽은 "둘 다 있을 때만 카드 결제 가능"으로 해석(한쪽만 있으면 설정 안 됨으로 취급, fail-closed) ③주기 점검 쿼리(어긋난 행 수를 세는 읽기 쿼리, 값 출력 없음)를 두 앱 운영 점검에 추가.

**모드 일치**: 저장 전 앱 코드에서 클라이언트 키와 시크릿 키의 모드가 같은지 검사(현행 유지). 클라이언트 키가 같은 가맹점의 짝인지는 서버가 확인할 수 없음(현행 한계, 설정 화면 안내 문구 유지).

## 10. 사장님 결정 사항

**확정**
1. 봉투 이름 `ENC:v2`, 앱 A 의 `ENC:v1` 은 읽기 전용 레거시.
2. 앱 B 도 전용 표로 옮긴다.
3. 알림톡은 묶음 전체를 한 암호문으로.
4. **공용 모듈**: platform-shared `secrets` 서브패스. push·태그는 앱 전환 시 별도 승인.
5. **마스터 키**: 앱·환경별 별도 키, 비밀번호 관리자에 환경별 분리 보관, 연 1회 교체.
9. 공개 클라이언트 키·provider 는 테넌트 소유 표에, 시크릿만 전용 표로. 앱 A 도 같은 방식.
10. **앱 B**: 저장·삭제·상태·암호문 조회 RPC 4종 + 기존 접속 기록 표 재사용.
11. **앱 B 이전 중 롤백**: 재입력 허용, 관찰 2~4주, 비우기 전 백업 확인 필수.
12. **알림톡**: 묶음 암호문 유지(공개/비밀 분리 안 함).
- 접속 기록 방침(사장님 지시): 키 저장·삭제·변경만 기록(값 제외), 복호화 읽기·상태 조회는 기록 안 함, 앱 A 도 앱 B 와 같은 방식.

- 코드·마이그레이션·환경변수·DB 변경, 커밋·push·태그. 구현은 설계 확정과 별도 승인 후.
- 앱 B 의 키 교체 가드 신설, 웹훅·환불 흐름 변경, 접근 통제의 다른 영역 재설계.
- 법·계약 판단.
- 키 값의 생성·전달(필요 시 사장님이 해당 환경에서 직접).

## 부록. 앱 A 담당 입력 반영 (2026-10-18, 정보 공유 수신)
- 1절 비교는 앱 A 담당 설명과 일치(표·RPC·AAD=테넌트·kid 없음·로테이션 불가·복호화 오류는 코드 문구만).
- 리허설·스테이징에 저장된 v1 암호문이 없다면 앱 A 는 **오픈 전에 v2 로 직행**하는 편이 이전 비용이 가장 작다(저장된 행 수 확인 필요; 결정 6).
- 앱 A 의 알림톡 로컬 구현은 같은 봉투를 쓰므로 공용 시그니처 확정 시 호출부만 따라가면 된다. 시그니처 변경 시 앱 A 담당에게 알린다.
- 앱 A 는 provider 허용 목록이 DB CHECK 제약이라 provider 추가마다 마이그가 든다(앱 B 새 표도 같음). 제약 방식 정리는 이 범위 밖.
- 마스터 키: 앱 A 리허설 있음, 스테이징 [미확인], 운영 미생성. 앱 B 쪽은 미확인.

## 부록 2. 앱 A 담당 입력 반영 (3판, 2026-10-18)
- 공개 키 저장 위치·읽기 경로·변경 규모는 6A 에 반영(코드 5~6, 시험 4~5, 후속 마이그 1+롤백).
- 마이그 적용 현황: 토스 키·팝빌 마이그는 스테이징·리허설에 적용됨(기록 기준, 이번에 DB 를 읽지 않음), 운영은 새 프로젝트가 아직 없음. 알림톡 마이그는 로컬 개발 DB·로컬 커밋에만 있고 어디에도 미적용·미push. 전용 비밀 표 행 수는 미확인(스테이징은 결제 스위치 꺼짐·키 입력 이력 없음, 리허설은 결제 키 설정 화면 시험 전 → 0 가능성 높음).
- 앱 A 방침: 한 번이라도 적용된 마이그 파일은 수정 금지, 후속 새 번호만. 미적용 로컬 전용 마이그(알림톡)는 수정 가능하나 로컬 롤백→재적용 시험과 커밋 승인 필요.
- 로그인 화주 화면의 카드 결제 가능 여부 확인 함수 import 는 미사용 잔여물(호출 없음) — 정리 여부는 앱 A 담당 몫.
- 앱 B 담당의 확인(파기 함수 최신 정의, 읽기 경로, 알림톡 발송 입구의 공급사 id) 도착 시 반영.

## 부록 3. 앱 B 담당 입력 반영 (3판 보정, 2026-10-18)
- **파기 함수**: 최신 정의(세 번 재정의된 것 중 마지막)가 탈퇴 5년 후 옛 비밀 컬럼을 NULL 처리하고 WHERE 조건에도 쓴다 → 컬럼 DROP 시 런타임 오류로 주간 파기 크론 실패(R5 정정: "조용히"가 아니라 실행 기록에는 남지만 파기 전체가 막힘). 안전 규칙: 컬럼을 NULL 만 하고 유지하는 동안은 안전, 삭제하려면 같은 마이그레이션에서 `pg_get_functiondef` 기준 재정의 + 새 표 행 삭제 추가.
- **공개 키 읽기 경로 확인**: 비로그인 상점 조회, 상점 액션의 결제 가능 여부, 결제 시작, 결제 화면 표시, 고객 관리 화면의 카드 허용 UI, 관리자 공급사 목록, PG 설정 저장·상태 — 모두 공급사 표의 공개 열을 세션/서버로 읽음 → 결정 9 와 맞음. 시크릿 복호화 경로 9곳(출고 후 환불·취소 2, 승인 콜백, 정합 크론, 웹훅, 불일치 점검 등)은 모두 한 도우미를 거침. 알림톡은 설정 확인(복호화 없이 존재만)과 발송 시 복호화가 분리돼 있음.
- **알림톡 입구**: 공급사 id 확보됨(R1 해소). **다중 소속 없음**·**슈퍼관리자 대행 저장 경로 없음**(5-3 갱신).
- **봉투·접속 기록 대조**: 1절 서술과 일치(앱 B 봉투 접두·버전 없음, AAD 없음, 키 하나). 이력 트리거는 공급사 표에 없음(R7 갱신).
- **저장된 건수(건수만, 값 없음)**: 스테이징 — PG 시크릿 암호문 1건(토스 테스트 키)·공개 클라이언트 키 1건·알림톡 0건. 리허설 — 공급사 0. 옛 운영 환경은 삭제됨, 새 운영은 아직 없음. 암호화 키 환경변수: 리허설 없음(확인), 스테이징 있을 것으로 추정(미확인), 운영 미확인.
- **이전 시 유의**: 환경마다 키가 달라 환경별 별도 백필, 통합 시험 5개 안팎이 옛 컬럼에 값을 심음, 공급사 이관 설계서에 새 표 추가(업체 uuid 보존이면 AAD 유지), 새 마이그 번호는 진행 중인 번호 이후.

## 부록 4. 접속 기록 확인 (4판)
- 앱 A: 앱 A 의 관리자 접근 기록 표는 관리자 RPC 전반이 쓰는 개인정보 접근·변경 기록(수정·삭제 금지 트리거, 정리 정책 없음으로 보임). 현재 키 관련 action 이름: 기존 결제 키 저장 기록 이름, 기존 알림톡 키 저장 기록 이름(로컬), 기존 세금계산서 키 저장 기록 이름(팝빌) [확인: 코드]. 로그인 이벤트 전용 표는 코드상 보이지 않음. 보관·조회 화면 유무는 앱 A 담당 답변으로 보정(아래 갱신란).
- 앱 B: 앱 B 의 접속 기록 표(로그인·접속 이벤트, 슈퍼관리자 조회, 2년 정리) [확인: 앱 B 담당].
- 앱 A 담당 답변(갱신): 로그인·접속 이벤트 전용 표는 **없음**(로그인 기록은 인증 서비스 자체 로그뿐). 앱 A 의 관리자 접근 기록 표는 보관·정리 정책이 **없고**(수정·삭제 금지, 크론·마이그에 정리 없음; 유일한 비우기는 오픈 전 일회성 수동 초기화 스크립트), **조회 화면·읽기 권한이 없다**(앱 코드에서 읽는 곳 없음, 클라이언트 직접 접근 불가 → 서비스 롤/DB 직접 조회만). `action` 은 CHECK 제약 없는 자유 텍스트라 새 어휘 도입에 스키마 변경이 필요 없다. 키 관련 기존 action 은 기존 키 저장 기록 이름 3종(결제·알림톡(로컬 미적용)·세금계산서(팝빌, 상세 형식 미확인)). 복호화 읽기는 현재도 기록하지 않아 사장님 지시와 이미 일치한다.
- 5A 안 1 영향: 앱 A 는 표 변경 없이 action 어휘만 바뀐다. 조회 수단이 없는 표이므로 "옛 이름과 새 이름을 모두 본다"는 점검은 DB 직접 조회 기준이다.
