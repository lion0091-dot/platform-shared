## 0. 한 줄 결론

1. 공용으로 뺄 가치가 있는 것은 **"계약과 순수 함수" 4가지뿐**이다: 분류 코드값, 상태 전이표(순수 함수), 개인정보 패턴 검사(순수 함수), 승격 규칙. 나머지(표·RLS·RPC·화면·알림·보관 정리)는 앱 몫이다. [근거: README 규칙 — 순수 함수·타입·계약만, DB·SQL·업무 규칙·비밀값 금지]
2. **세 앱의 DB와 로그인은 서로 분리돼 있어 "한 곳에서 모아 보기"는 앱 DB를 건드리지 않고는 불가능하다.** 현실적 안은 (A) 앱별 따로(권장 시작점)와 (B) 모아 보기(별도 수신 서비스 필요, 확장안)다. 3절.
3. 공용 버전은 **무태그 유지 방침과 별개로 새 서브패스 `./board` 하나를 추가하는 것**이라 새 태그가 필요하다(§6). 기존 서브패스·공개 API는 바뀌지 않는다.
4. 최소안은 "공용 계약 문서 + 코드값·전이표·패턴 검사 서브패스 1개"이고, 앱별 구현은 shipping 이 먼저(설계안 완성도가 가장 높음).

## 1. 공용과 앱 몫의 경계

README 규칙을 기준으로 판정했다. "공용"은 `@platform/shared/board` 서브패스(순수 TypeScript, 부작용·네트워크·DB 없음) 후보다.

| 항목 | 판정 | 이유 |
|---|---|---|
| 분류 코드값(1층·2층) | **공용** | 문자열 상수와 타입. 분석 조회(§5)가 앱이 달라도 같은 값을 읽게 하는 것이 핵심 이득. 값 목록은 §4-1 |
| 2층 상태값과 전이표(`RECEIVED→IN_PROGRESS` 등) | **공용** | 순수한 "허용 전이 + 누가 바꿀 수 있나(역할 종류 TENANT/PLATFORM)" 표와 `canTransition(from,to,actor)` 함수. DB 함수가 이 표를 똑같이 강제하는 것은 앱 몫(앱의 기존 주문 전이표와 같은 "코드 표 + DB 함수 동기화" 규칙, 같은 이유로 시험 벡터를 함께 둔다) |
| 개인정보 패턴 검사 | **공용(순수 함수만)** | `detectPii(text)` → 발견 종류 목록(전화·주민번호 형태·계좌 형태·이메일). 서버가 저장 전에 호출해 거부한다. 정규식·알고리즘은 공개해도 무방(서명 방식과 같은 판단, 2026-10-13 결정). 한계는 §4-2 |
| 승격 규칙 | **공용(순수 함수 + 계약 문서)** | 승격 가능 조건(1층 글·숨김 아님·개인정보 확인 체크·분류 선택·사유 길이)을 `validateEscalation(input)` 으로. 누가 승격할 수 있나(대표·경리)는 **역할 이름이 앱마다 달라** 함수는 "권한 있음/없음" 불리언만 받는다 |
| 글/답글 길이 한도(제목 100·본문 2000·사유 200) | **공용(상수)** | 세 앱이 같은 값을 쓰면 승격·분석 때 일관됨. 앱이 더 좁게는 가능 |
| RPC/표 인터페이스 계약 | **공용(문서)** `docs/board-contract.md` | 열 이름·허용 값·RPC 이름·오류 코드(`ALREADY_PROCESSED` 등)를 문서로만 고정. SQL 은 넣지 않는다(README). 이 계약이 있어야 §5 분석 조회·§3-B 모아 보기가 앱이 달라도 같은 모양이 된다 |

| 표(`board_posts`·`board_replies`)·RLS·RPC·트리거 | **앱 몫** | SQL·DB 구조라 공용 금지. 앱의 테넌트·역할 구조가 다름(§2) |
| 알림·푸시 | **앱 몫** | 앱마다 알림 기반이 다름(앱별로 다름). 공용은 이미 `push/fcm`, `push/native` 가 있고 이 설계에서 더 얹지 않는다 |
| 보관 정리(크론) | **앱 몫** | 서비스 롤·DB 작업. 기간 값만 계약 문서에 "법무 확정값" 으로 적는다 |
| 화면 컴포넌트(목록·상세·작성 폼) | **공용 안 함** | 앱마다 UI 시스템이 다르고(Next 앱 둘 + ledgercore 는 자체 컴포넌트) 공용 패키지에 React 컴포넌트를 넣은 선례가 없다(`push/native` 는 Capacitor 로직뿐, 화면 없음). 공용 코드가 화면을 가지면 세 앱의 디자인 변경이 서로 발목을 잡는다. **작성 안내 문구 상수**(개인정보 쓰지 말라는 문구)만 공용으로 두는 선택지는 있음 [결정 5] |
| 접근 기록(감사) | **앱 몫** | 앱마다 감사 표가 다름 [확인] |
| 분석 조회용 읽기 전용 뷰·계정 | **앱 몫(계약은 공용)** | §5 |

공용에 넣지 않기로 한 것은 "화면", "알림", "표/SQL", "보관 정리", "읽기 전용 계정 스크립트"다.

## 2. 세 앱 차이 (계약 수준 요약)

| 항목 | 앱 A (도매) | 앱 B (회계) | 앱 C (물류) |
|---|---|---|---|
| 테넌트 단위 | 공급사 | 회사 | 운영사 |
| 테넌트 안 역할 | 대표·매니저·직원 계열 | 회사별 사용자 정의 역할 | 대표·경리·일반 직원 |
| 테넌트 밖 사용자 | 고객, 슈퍼관리자 | 없음 | 화주, 차주 |
| 플랫폼 운영자 | 앱 내부 계정 | 전용 구조 없음(도입 시 설계 필요) | 앱 내부 계정 |

공통점: 세 앱 모두 (1) 테넌트 격리 단위가 있고, (2) 플랫폼 운영자가 테넌트 업무 데이터를 직접 보지 않는 원칙이다.
차이점의 핵심 두 가지: **테넌트 안 역할이 앱마다 다르다**(공용 코드가 역할 이름을 가정하면 안 됨), **한 앱은 플랫폼 운영자 구조가 아직 없다**(게시판 2층의 수신자 문제 → 도입 순서에 영향, §6).
각 앱의 내부 구조(표·정책·운영 방식)는 공개 저장소에서 다루지 않는다.

## 3. 플랫폼 운영자 계정과 통합 수신함

### 3-1. 현재 사실
- 계정은 **앱마다 따로**다. 세 앱의 로그인 사용자 표가 서로 다르고, 한 사람이 세 계정을 가진다 [확인: 위 표].
- 세 앱 DB 는 서로 분리돼 있다. 앱 간 연결은 ledgercore 와 wholesale·shipping 사이의 서명된 HTTP 호출(`@platform/shared/account`)과 SSO 뿐이며, 게시판 같은 데이터를 앱 간에 밀어 넣는 경로는 없다 [확인].
- 일부 앱은 운영사별 푸시를 플랫폼 운영자에게 보내지 못한다(구독 저장 대상이 직원·차주뿐). 다른 앱은 앱 담당 확인 필요.

### 3-2. 두 가지 안

| | **A. 앱별 따로 (권장 시작점)** | **B. 모아 보기** |
|---|---|---|
| 구조 | 각 앱의 플랫폼 운영자 화면에서 그 앱의 2층 글만 본다. 개발자는 앱 3곳에 각각 로그인 | 별도의 "수신 서비스"(새 앱 또는 새 Supabase 프로젝트)가 세 앱의 2층 글을 한 곳에 모은다 |
| 모으는 방법(하위 선택) | — | ① **밀어넣기**: 승격 시 앱 서버가 수신 서비스로 서명 호출(기존 `buildSignedCall` 방식 재사용 가능). 본문이 앱 밖으로 나가므로 개인정보 검사가 이중 필요 ② **끌어오기**: 수신 서비스가 앱별 읽기 전용 뷰를 주기 조회(§5 와 같은 구조). 앱마다 읽기 전용 DB 계정·네트워크 허용이 필요 ③ **웹훅 알림만**: 수신함에는 "글 도착" 신호(id·앱·분류)만 오고 본문은 앱에서 본다 |
| 새로 필요한 것 | 없음(앱별 구현만) | 새 서비스 1개 + 앱↔서비스 계약(인증·재전송·중복 제거) + 서비스의 계정·감사·보관 정책 + 운영·배포 + 비밀값(서명 키·읽기 전용 계정 비밀번호) 관리 |
| 개발자 불편 | 앱 3곳을 돌아야 함 | 해소 |
| 개인정보 | 본문이 앱 안에 머묾(수탁 범위가 앱별로 단순) | ① 은 본문이 제3의 저장소로 복제됨 → **[법무]** 처리 위탁·보관 위치 재검토. ② 는 본문 복제 없이 조회만(권장), ③ 은 가장 안전 |
| 비용·위험 | 가장 낮음. 이미 세 앱이 각자 플랫폼 화면을 가졌거나 만들 예정 | **[추정]** 구현·시험 앱별 1~2일 + 서비스 구축 5일 이상, 이후 운영 비용(호스팅, 크론, 장애 대응). **새 서비스·새 인프라라 CLAUDE.md Level 3(구조·운영 복잡도)** → 개발자 승인 필수 |
| 되돌리기 | 쉬움(앱별 기능 스위치 끄기) | 서비스가 한 번 돌기 시작하면 데이터 이전·폐기 절차 필요 |

### 3-3. 권장
1. **시작은 A.** 앱별 2층 글 수신 화면만 만든다. 개발자 한 명이 하루 몇 번 열어 보는 규모에서 3곳 순회는 감당 가능하다 [추정, 예상 건수 미확인 → 결정 4].
2. **B 로 가는 길을 막지 않도록** 지금 정해 둘 것(비용 거의 없음): ① 분류·상태·시각 열을 세 앱이 같은 이름·값으로 둔다(§4, §5) ② 각 앱에 **2층 전용 읽기 전용 뷰**를 허용 가능하게 설계한다(승격된 글만) ③ 글 id 는 앱 안에서 유일하고, 모아 볼 때는 `(app_key, post_id)` 쌍으로 식별한다(`app_key` 값은 공용 상수: `MEAT`·`SHIP`·`LEDGER` 등 [결정 6]).
3. B 를 정말 원하면 **③(알림만) → ②(끌어오기)** 순으로 단계적으로, 새 서비스 없이 갈 수 있는지 먼저 본다: 예) 앱별 알림이 개발자 이메일·푸시로 오게 하면 "모아 보기" 요구의 상당 부분이 해소된다 [추정, 결정 4].
4. 앱 내부 플랫폼 운영자 계정은 **그대로 앱별**(앱별 계정 구조 유지). 이 설계를 이유로 계정 구조를 합치지 않는다.

## 4. 개인정보 · 보관 기간 공통 규칙

### 4-1. 코드값 (공용 상수 후보, 이 값은 shipping 설계안에서 가져와 재판단)
- 1층 분류(`tier=1`): `NOTICE`(공지) · `QUESTION`(문의) · `HANDOVER`(인수인계). 앱이 더 추가 가능하나 분석 조회 대상은 아님(1층 본문은 분석 제외, §5). 결정 7.
- 2층 분류(`tier=2`, 승격 시 선택): `BUG`(오류) · `FEATURE`(기능 요청) · `ACCOUNT`(계정·권한) · `ETC`(기타). **청구·계약 문의는 2층에 넣지 않는다**(앱 설계안, [변호사] 확인 전까지) [결정 8].
- 2층 상태: `RECEIVED` · `IN_PROGRESS` · `NEED_INFO` · `DONE` · `DECLINED`. 1층 글은 상태 `NONE`.
- 답글 가시성: `TENANT_ONLY`(직원 내부 메모) · `AUTHOR`(작성자에게 보이는 답) · `PLATFORM`(2층 답) — **개정으로 3값**(§9-2c). 아래 §5·§9-1 의 `TENANT_ONLY` 표현은 이 의미로 읽는다.
- 작성 측: `TENANT` · `PLATFORM`. 작성자 유형 `author_kind`(`STAFF`/`USER`)는 글·답글 모두 별도 열(§9-1, §9-6).

### 4-2. 전이표 (shipping 설계안 §6 을 공용화)
| 현재 | 다음 | 누가 |
|---|---|---|
| (1층 글) NONE | RECEIVED(승격) | TENANT(승격 권한자) — 한 방향, 되돌림 없음 |
| RECEIVED | IN_PROGRESS · NEED_INFO · DONE · DECLINED | PLATFORM |
| IN_PROGRESS | NEED_INFO · DONE · DECLINED | PLATFORM |
| NEED_INFO | RECEIVED | TENANT(답글로 보충) |
| DONE | RECEIVED(재오픈) | TENANT(승격 권한자), [결정 9] |
| DECLINED | — | 사유 필수. 재문의는 새 글 |
- `DECLINED`·`NEED_INFO` 로 갈 때 사유(답글) 필수 여부는 계약에 "필수"로 둔다.
- 순수 함수: `canTransition(from, to, actorSide)`, `requiresReason(to)`. DB 는 이 표를 `for update` + `ALREADY_PROCESSED` 로 강제(앱 몫).

## 5. 장래 읽기 전용 분석 조회의 공통 조건 (분석 기능은 만들지 않음)

선례: 읽기 전용 DB 계정(열 단위 권한) 선례. 같은 모양으로 앱마다 **2층 전용 뷰**를 두면 장래 개발자 구독 Claude 가 주기적으로 읽기 전용 조회할 수 있다.

세 앱이 **같은 이름·값으로** 지켜야 할 조건(공용 계약 문서에 고정):
1. **뷰 이름·열**: `board_escalations_v` (이름은 [결정 6]에서 확정). 열: `app_key`, `post_id`, `tenant_id`(분석용 가명 id, 앱 안에서만 의미), `category`(§4-1 코드값), `escalation_status`(§4-1), `created_at`(1층 작성), `escalated_at`, `first_response_at`(첫 PLATFORM 답글), `closed_at`(DONE/DECLINED 시각), `updated_at`, `title`, `body`(§4-4 에 따라 삭제되면 null), `reply_count`.
2. **필터 가능**: `tier=2`(승격된 글만)이 뷰 조건. 1층 글은 뷰에 **행도 열도 없다** → 건수에도 안 잡힘(의뢰 조건).
3. **1층 본문 제외**: 뷰는 1층 `body`·1층 답글(`TENANT_ONLY`)을 아예 포함하지 않는다. 승격 때 넘기는 것은 본문+사유뿐(앱 설계안의 승격 범위 권장안과 같음).
4. **시각은 모두 `timestamptz`(UTC)**. 처리 시간·응답 시간 분석이 가능해야 한다.
5. **분류는 고정 코드값**(자유 입력 금지). 코드 목록 버전을 계약에 적는다(`board_contract_version`).
6. **작성자 식별 제외**: 뷰에 작성자 id·이름·이메일 없음. 테넌트 이름 노출 여부는 [결정 3]에 따라 앱별로 가명 id 로 대체 가능.
7. **읽기 전용 계정**: 뷰 하나에만 `SELECT`, `INSERT/UPDATE/DELETE` 불가, 다른 표 접근 불가, 접속 허용 목록·사용 기록. 계정·비밀번호 관리는 앱 담당(비밀값은 저장소·문서·채팅 금지).
8. **개인정보**: 뷰에 올라오는 본문도 §4-3 패턴 거부를 거친 값이어야 한다. 본문 삭제(§4-4)가 뷰에 즉시 반영돼야 한다.
9. **계약 버전**: 열 추가는 하위 호환(분석 쪽이 모르는 열은 무시), 열 이름·값 변경은 계약 버전을 올린다.
- 이 설계에서 **만들지 않는 것**: 읽기 전용 계정 자체, 주기 조회 크론, 분석 로직, 요약·알림.

앱 설계안의 결정 3(1층 작성자 범위), 4(승격 권한=대표·경리), 7(본문 지우기 권한), 9(정지·만료 운영사 2층 허용), 12(승격 시 넘길 범위)는 **앱의 역할 구조에 따라 달라지므로 앱별로 결정**한다. 공용은 "승격 권한 있음" 불리언 입력만 받는다.

## 9. 보완: 일반 사용자 작성 · 3개 진입 · 스팸 · 경계 (2026-11-04 개정)

### 9-1. 작성자 유형과 가시 범위 (공용 계약)
- 새 열 `author_kind`(코드값): `STAFF`(운영사 직원: 대표·경리·일반 직원 등 테넌트 업무 권한자) · `USER`(테넌트 소속 일반 사용자). 기존 `author_side`(TENANT/PLATFORM, 답글 쪽 표시)와 별개다. `PLATFORM` 은 답글에만 있고 글의 `author_kind` 는 `STAFF`/`USER` 둘뿐.
- 공용 함수 `canView(post, viewer)`, `canReply`, `canEscalate`(계약용 순수 함수. 입력은 `viewerKind`(`STAFF`/`USER`/`PLATFORM`), `isAuthor`, `tier`):
  | 보는 사람 | 1층 글 | 1층 답글 | 2층 글(승격본) |
  |---|---|---|---|
  | `USER` | 자기가 쓴 글만 | 자기 글에 달린 답글만 | **안 보임**(승격 사실도 노출 안 함 [결정 14]) |
  | `STAFF` | 자기 테넌트 전부 | 전부 | 자기 테넌트가 올린 것 + 플랫폼 답변 |
  | `PLATFORM` | **안 보임(건수에도 없음)** | 안 보임 | 승격된 것만 |
- **승격 권한**: `STAFF` 중 앱이 "대표·경리급" 으로 판정한 사람만(`canEscalate` 는 앱이 넘기는 불리언 `hasEscalateRole` 을 받음. 역할 이름은 앱마다 달라 공용이 모름 — 본문 §1).
- 일반 사용자 글을 승격할 때 **작성자 유형·이름·연락처는 2층에 넘기지 않는다**(`author_kind` 도 넘기지 않음). 1층 대화(답글)도 안 넘기고 본문+승격 사유만(기존 권장 유지). 승격 시 운영사 직원이 본문을 **다시 읽고 편집 가능**하게 하는 안은 추가 [결정 15]: 일반 사용자가 쓴 본문이 개인정보를 가졌을 확률이 높으므로, 승격 직전 `detectPii` 재검사 + 체크 필수를 강제(§9-3).
- 답글 가시성 `TENANT_ONLY` 는 **일반 사용자에게도 보이는 답글**(그 글 작성자에게 보이는 직원 답)과 구분이 필요하다. 코드값 정리: 1층 답글은 `AUTHOR`(작성자에게 공개) · `TENANT_ONLY`(직원 메모, 일반 사용자에게 안 보임)로 나눈다 [결정 16, 이름은 §9-2c 로 통일]. `PLATFORM` 은 2층 답글 그대로.

### 9-2c. 앱 대조 결과 반영
- **일치**: 분류·상태 코드값, 글 길이(100/2000/200), 전이표는 사실상 일치. 공용안 채택 차이: `DECLINED` 는 종결, 사유 필수는 `DECLINED`·`NEED_INFO`, 뷰 열 `first_response_at`·`reply_count`·`app_key('SHIP')` 추가, `detectPii` 이메일 패턴 포함.
- **작성자 종류는 앱이 정의**한다. 공용 계약은 두 겹으로 둔다: ① `author_kind` = `STAFF` · `USER`(공용, §9-1) ② `author_role` = 앱 정의 하위 구분(문자열, 공용은 형식만 규정: 영문 대문자·밑줄 32자 이하). shipping = `SHIPPER` / `DRIVER` / `STAFF`, wholesale = `RETAILER` / `OWNER` / `MANAGER` / `STAFF`, ledgercore = `STAFF` 계열만. 분석 뷰에는 둘 다 넣지 않는다(§9-6).
- **분류는 작성자 종류별 허용 목록**: `NOTICE`·`HANDOVER` 는 `STAFF` 전용, `USER` 는 `QUESTION` 과 (선택) `SUGGESTION` 만. 허용 목록 표는 공용 상수 `ALLOWED_CATEGORIES_BY_KIND`.
- **답글 가시성은 shipping 이 이미 쓰는 이름으로 통일**(변경 최소): `TENANT_ONLY`(직원 내부 메모) · `AUTHOR`(작성자에게 보이는 답) · `PLATFORM`(2층 답, 직원만 보고 일반 사용자에겐 안 보임). 앞 §9-1·§9-6 의 `STAFF_ONLY`/`VISIBLE_TO_AUTHOR` 는 이 이름으로 읽는다 (`STAFF_ONLY`→`TENANT_ONLY`, `VISIBLE_TO_AUTHOR`→`AUTHOR`).
- **작성 대상 테넌트는 화면에서 고른 값으로 고정**하는 규칙을 공용 계약에 넣는다. 이유: 차주는 운영사 여럿에 속할 수 있고 현재 테넌트를 세션에서 얻는 방식이 차주에게는 맞지 않아 차주용 RPC 가 별도로 필요할 수 있다. 규칙: `tenant_id` 는 호출 인자로 받되 서버가 (사용자, 테넌트) 소속을 검증, 소속 아니면 `NOT_VISIBLE`. wholesale 고객도 같은 규칙(현재 보는 공급사).
- **쓰기 경로 충돌(실제 충돌 1곳)**: 공용안은 "서버가 저장 전에 `detectPii`" 인데 쓰기 RPC 가 인증 사용자에게 직접 열려 있으면 서버 검사를 우회할 수 있다. 계약 문구(안):
  > **글·답글을 저장하는 유일한 경로는 서버 액션이다.** 쓰기 RPC 는 `service_role` 전용으로 하고 서버 액션만 호출한다. 서버 액션은 (1) 세션에서 사용자·역할 확인 (2) `detectPii`·길이·분류 허용 목록·작성 제한 검사 (3) RPC 에 `p_actor`(사용자 id)와 `tenant_id` 를 넘긴다. RPC 는 서비스 키만 믿지 않고 **DB 안에서 `p_actor` 의 테넌트 소속과 권한을 다시 검사**한다(account `platform_*` 의 이중 방어 패턴). 읽기 RPC 는 `authenticated` 로 열어도 되나 반환은 가시 범위(§9-1)를 DB 안에서 강제한다.
  - 대안 (나): 같은 정규식을 SQL 에도 구현 — 두 구현이 어긋날 위험이 크고 SQL 정규식 유지 부담이 있어 비권장. 공용 시험 벡터 대조로 어긋남을 잡을 수는 있다.
  - 권장 (가). 대가: 서버 액션이 곧 보안 경계라 `p_actor` 를 위조하지 못하도록 서버 코드 검토가 필요. [결정 28]
- **계약 변경 비용**: 앱의 공용 라이브러리 핀을 올려야 하고 CHECK·뷰를 재정렬해야 하므로 **앱이 마이그를 쓰기 전에 `board_contract_version` 을 확정**해야 한다 → 공용 `./board` 첫 태그와 계약 v1 을 함께 확정한 뒤 앱 마이그 작성(§6-1 순서 1→2 를 엄격히). 계약 v1 이 바뀌면 앱 마이그가 어긋나므로 확정 전 앱 마이그 작성 금지.
- **남용 방지 추가**: 사용자별 레이트 제한 + **열린 글 상한**(미해결 글 N건 초과 시 새 글 거부, 직원 답 후 다시 가능) [결정 19 에 포함].
- **알림**(앱 몫, 공용은 이벤트 이름만 문서화): 이벤트 `POST_CREATED`(직원에게) · `AUTHOR_REPLIED`(작성자에게) · `ESCALATED_RECEIVED`(플랫폼) · `PLATFORM_REPLIED`(직원). shipping: 직원 새 글 알림 대상은 대표·경리만(기존 알림 수단 재사용) [결정 29 결정됨], 작성자 답 알림은 차주 푸시 가능·화주 앱 안 알림만. wholesale: 대표·매니저 알림함 선례. ledgercore: 알림 없음, 배지만.
- **차주 PENDING(소속 승인 전) 작성: 불허 [결정 30 결정됨]** — 소속이 확정되지 않은 사용자가 테넌트 직원에게 글을 올리게 하면 스팸·개인정보 경로가 되고, 승인 문의는 기존 가입 안내로 충분].
- **진입 위치 (개정 2 로 최종)**: **대문에는 링크를 두지 않는다**(대문 변경·시험·링크 위치·로그인 복귀 처리 논의 모두 범위에서 삭제). 진입점은 3곳뿐: 화주 = 화주 메뉴의 「문의」 항목+기능 스위치, 차주 = 하단 탭 증설 대신 「내 정보」 안이나 상단바, 운영사 직원 = 관리자 메뉴. 비로그인 화주 문의는 기존 발주 문의 유지(§9-2d).

### 9-2d. 비로그인 화주 A안: 기존 발주 문의를 직원 1층 수신함에 함께 보이기 (앱 C 기준)
- 결정: **기존 발주 문의 기능을 그대로 유지**하고, 직원 수신함에서 게시판 1층 글과 **함께 보이게만** 한다. 답은 전화·문자(게시판 답글 없음). 새 익명 글쓰기·새 공개 입구 없음.
- **합산 방식(권장 = 읽기 전용 합산, 표 합치지 않음)**: 직원용 읽기 RPC 하나가 두 원천을 합쳐 공통 모양(원천 구분, id, 요약, 작성자 표시, 작성 시각, 원천 상태)으로 돌려준다. 상태는 **원천별 상태를 그대로** 표시하고 통합 상태값을 새로 만들지 않는다(전이표가 다름). 항목을 열면 원천별 기존 화면으로 이동해 처리 로직을 재사용한다.
- 영향 범위: 기존 발주 문의 표·RPC는 **변경 없음**(읽기 합산만). 공용(`@platform/shared`)은 **영향 없음** — 발주 문의는 공용 계약 밖(앱 고유)이며 합산 뷰는 공용 계약에 넣지 않는다.
- 개인정보: 발주 문의에는 전화번호가 들어 있으므로 합산 뷰는 **직원 전용**(자기 운영사)이고, 플랫폼 운영자·2층 분석 뷰·읽기 전용 계정에는 **포함하지 않는다**. 보관은 기존 발주 문의 정리 규칙을 유지하고 게시판 보관 기간과 합치지 않는다 [법무 참고].
- 승격: 발주 문의는 **2층으로 승격하지 못한다**(주문 문의이지 기술 문제가 아님). 수신함 목록에서도 승격 버튼은 게시판 항목에만 둔다.
- **처리 필요 건수(배지) — 결정 33 확정**: 정의 = **「직원 답을 기다리는 건」**. 구성: ① 신규 발주 문의(아직 연락하지 않은 건) ② 직원이 아직 답하지 않은 1층 글 ③ 직원이 답한 뒤 작성자가 다시 쓴 1층 글(**마지막 답글의 작성자가 직원이 아닌 경우**). 합산 수신함의 「처리 필요」 필터와 메뉴 배지가 같은 정의를 쓴다(이미 연락·전환·종료된 발주 문의, 직원이 마지막으로 답한 글, 종료·숨김 글은 제외). 판정은 **답글의 작성자 유형 열**(`author_kind`, §9-1)로 한다 → **공용 계약: 답글도 `author_kind`(STAFF/USER) 열을 가진다**(글과 같은 값, 답글 `author_side` TENANT/PLATFORM 과 별개). 2층 글은 이 건수에 포함하지 않는다(직원이 아니라 플랫폼이 답할 차례).
- 시험: 격리(타 운영사 문의가 합산에 안 섞임), 비직원 호출 거부, 플랫폼 운영자 호출 거부, 원천별 건수 합과 배지 일치.
- 다른 앱: 앱 A(도매)·앱 B(회계)는 해당 없음(비로그인 접수 문의 기능 없음). 둘은 1층 수신함이 게시판만으로 구성된다.
- 대안(비권장): 발주 문의를 게시판 글로 변환·복사 — 전화번호가 본문(`detectPii` 대상)에 들어가 거부되며 표·상태 이중화 위험.

### 9-4. 스팸 · 도배 제한
- **익명 작성 금지**(결정 반영): 로그인한 `user_id` 가 없는 작성은 허용하지 않는다. 대문에는 게시판 링크도 두지 않는다(개정 2).
- 사용자별 작성 제한은 **필요하다**(일반 사용자 풀은 외부 대중에 가깝고 계정 생성이 쉬움): 공용 계약에 **기본값 제안**을 명시하고 값은 앱 설정으로 둔다.
  - 일반 사용자: 하루 글 N건(예 5), 분당 1건, 같은 내용 반복 거부(해시 비교는 앱), 미승인(승인 대기) 계정은 작성 불가.
  - 직원: 완화(예 하루 30건) — 도배보다 실수 방지 목적.
  - 한도 초과 오류 코드값: `RATE_LIMITED`. 공용은 **상수와 판단 함수 `exceedsLimit(counts, kind)` 정도**만(카운트 조회는 DB 라 앱 몫).
- 제한 대상 수치는 [결정 19]. 시행 위치는 서버 RPC(클라이언트 제한은 무의미).
- 정지·탈퇴 사용자: 새 글 불가, 기존 글은 직원이 열람(테넌트 업무 기록) — 탈퇴 시 본문 처리는 [법무] 개인정보 보관 규정과 연동.
- 직원 신고·차단: 직원이 특정 일반 사용자의 작성 권한을 막는 기능은 **확장안**(최소안은 "숨김"만).

### 9-5. 기존 분쟁 · 발주 문의와 경계 (문구)
공용 상수 `BOARD_SCOPE_NOTICE`(작성 폼 위 안내, 앱이 한글로 다듬음) 초안:
> 이 게시판은 **일반 문의와 안내** 용도입니다. 주문·배송·금액에 관한 문제는 해당 주문 화면의 **분쟁(문의) 기능**을, 접수 전 문의는 **발주 문의**를 이용해 주세요. 주문 번호와 금액 확인이 필요한 일은 게시판에 쓰지 마세요.
- 앱 C 기존 기능: 주문에 묶인 분쟁, 비로그인 화주의 발주 문의. 게시판은 이 둘과 **표·화면·알림을 공유하지 않는다**.
- 앱이 분류 `ORDER_RELATED`(안내 전용)를 둘지: 작성 중 이 분류를 고르면 저장하지 않고 안내 문구로 보내는 방식도 가능하나, 코드값은 늘리지 않는다 [결정 20, 권장 안 함].
- wholesale·ledgercore 의 기존 대응 기능(분쟁·문의 화면)은 [미확인].

## 11. 첨부 파일 (2026-11-04 개발자 결정으로 추가 — 이 절이 §4-3·§6-3·§9-3·§9-7 의 "첨부 없음" 을 뒤집는다)

**개발자 결정(11-04)**: 2층 게시판은 첨부 파일 업로드를 지원한다. 드래그앤드롭이면 더 좋다. 결정 #34~#45 는 **모두 권장대로 확정**됐다(§11-11). 이 절의 표·상수는 확정값이며, 미확정은 사전 확인 3건뿐이다. 구현·코드·커밋·push·태그 없음.

### 11-1. 한눈에
- 첨부는 **2층(기술 문의)에만** 있다. **1층은 첨부 불가**(결정 #40, 확정).
- 파일은 **앱별 비공개 버킷**에 두고, 열람은 **짧은 서명 URL**로만 한다. 업로드는 **서버를 거친다**(브라우저가 스토리지에 직접 올리지 않음).
- 공용(`@platform/shared/board`)은 **상수와 순수 검사 함수만** 둔다(파일 바이트를 저장·전송하지 않음, 비밀·SQL 없음 — README 원칙 유지). 저장·권한·정리는 앱 몫. **드래그앤드롭은 화면 몫**이라 공용 계약에 없다.
- 개인정보: 스크린샷·문서는 `detectPii` 로 못 거른다 → 사람이 확인하는 체크(11-4)와 EXIF 제거로 보완하고, 한계를 계약에 명시한다.

| `BOARD_ATTACH_MAX_BYTES` | 파일 1개 **4MB** (결정 #48 로 5MB → 4MB 갱신, 확정) | 서버 경유 업로드가 요청 본문 한도(약 4.5MB 추정)에 걸리지 않게 함 |
| `BOARD_ATTACH_MAX_TOTAL_BYTES` | 건당 합계 **15MB** | 비용 상한 |
| `BOARD_ATTACH_ALLOWED` | 이미지 `jpg·png·webp`, 문서 `pdf`, 텍스트 `txt·log`(오류 로그용) | **허용 목록 방식**(금지 목록 아님). `heic` 는 브라우저에서 못 보여 제외 권장. 동영상·압축파일·오피스 파일(`docx·xlsx`, 매크로 위험)은 최소안에서 제외 |
| `BOARD_ATTACH_BLOCKED_EXT` | 실행·스크립트·압축 형식 일체(`exe·bat·cmd·ps1·sh·js·vbs·msi·dll·jar·apk·scr·com·html·htm·svg·zip·7z·rar` 등) | 허용 목록 밖은 어차피 거부이므로 **이중 안전망**. 특히 `svg`·`html` 은 스크립트가 들어갈 수 있어 이미지로 취급하지 않음 |
| `BOARD_ATTACH_NAME_MAX` | 표시 이름 100자 | |

**공용 순수 함수 후보**: `validateAttachmentMeta({name, size, declaredMime, head})` — 이름·크기·확장자·**앞부분 바이트(매직 바이트)** 를 받아 허용 여부와 판정 형식을 돌려줌(파일 전체를 받지 않음; 앞부분 1KB 정도면 판정 가능). `sanitizeDisplayName(name)`. `exceedsAttachLimit(count, totalBytes)`. 시험 벡터는 `__vectors__/attachments.json`(허용·거부·이중확장자·가짜 확장자 등).

**오류 코드 후보(추가)**: `ATTACH_TOO_MANY`, `ATTACH_TOO_LARGE`, `ATTACH_TYPE_NOT_ALLOWED`, `ATTACH_CONTENT_MISMATCH`(확장자와 내용 불일치), `ATTACH_NAME_INVALID`, `ATTACH_NOT_FOUND`, `ATTACH_PRIVACY_NOT_CONFIRMED`(11-4 체크 누락), 기존 `NOT_VISIBLE`·`RATE_LIMITED` 재사용.

### 11-3. 저장 · 접근 · 업로드 경로
| 항목 | 설계 | 공용/앱 |
|---|---|---|
| 버킷 | 앱별 **비공개** 버킷 1개(`board-attachments`). 공개 URL 없음. | 앱 |
| 버킷 제한 | 버킷 자체에 `file_size_limit`·`allowed_mime_types` 를 건다 — 서버 액션이 검사해도 스토리지 API 직접 호출은 우회하므로 **뒷문 방어** | 앱 |
| 업로드 | **서버 액션(서버 경유)이 유일한 경로, 요청 1건에 파일 1개**(결정 #46 확정, §11-12). 브라우저 → 서버 액션 → 검사 → 저장 → 메타 행 생성. 저장 주체는 기본 `service_role`(스토리지 `authenticated` INSERT 정책 없음, 결정 #28 과 동일)이나 **앱 관례에 따라 다를 수 있다**(결정 #49 확정): 계약은 결과 규칙만 요구하고, 세션+RLS 관례를 쓰는 앱에서 `service_role` Storage 쓰기를 새로 도입하려면 별도 승인 | 앱 |
| 검사 순서 | ① 로그인·소속(대상 테넌트) ② 글 가시성(`canView`) ③ 개수·용량 ④ 이름 정리 ⑤ **매직 바이트 판정**(`validateAttachmentMeta`) ⑥ 개인정보 확인 체크 ⑦ 저장 ⑧ 메타 행 | 순서·함수는 공용 계약, 실행은 앱 |
| 읽기 | 메타 목록은 글과 같은 가시성 RPC. 파일은 **서명 URL(권장 10분)** 을 서버가 발급(권장 10분). **발급 직전에 권한을 다시 확인**하고, 사용자가 URL 을 공유해도 시한 뒤 만료 | 앱 |
| 접근 범위 | **해당 운영사 직원 + 플랫폼 운영자**(2층 글에 한함). 일반 사용자는 **자기 글의 첨부만**(1층과 같은 규칙, 2층 글은 승격 후 일반 사용자가 못 봄 — §9-1). 플랫폼 운영자의 열람은 접근 기록(§4-3)에 (글 id, 첨부 id, 시각) | 앱(RPC 에서 강제) |
| 다운로드 | `Content-Disposition: attachment` 로 내려 브라우저가 파일을 **실행·렌더하지 않게** 한다(이미지 미리보기는 `<img>` 로만, 서명 URL 도메인은 앱 도메인과 분리됨) | 앱 |
| 승격 시 | 1층에는 첨부가 없으므로(결정 #40) 승격으로 넘어오는 첨부도 없다. 직원이 **승격 뒤 2층에서** 첨부를 올린다 | 앱 |

### 11-4. 개인정보 · 파일명 · EXIF
| 대책 | 내용 |
|---|---|
| **「개인정보 가림 확인」 체크(필수)** | 업로드(또는 글 등록·승격) 때 "첨부에 이름·연락처·주소·계좌·차량번호·고객 정보가 보이지 않음을 확인했습니다" 체크 필요. 서버가 체크 값을 요구(`ATTACH_PRIVACY_NOT_CONFIRMED`). 글 1건당 1회 체크(파일마다 반복하지 않음, 결정 #43). **서버가 강제하고 확인한 사람·시각을 기록**(`privacy_confirmed_by`·`privacy_confirmed_at`). 최종 책임은 테넌트(§4-3 승격 확인과 같은 구조). 체크 문구는 공용 상수 후보 |
| 작성 안내 | 첨부 영역에 상시 문구: "화면 캡처에서 개인정보·거래처 정보는 가려서 올려 주세요" + `detectPii` 가 첨부에는 **작동하지 않음**을 계약에 명시 |
| 한계 | 이미지 속 글자는 못 거른다(OCR 은 하지 않음 — 비용·오탐·새 위탁 발생, 하지 않기를 권장). 따라서 "차단"이 아니라 "확인 절차 + 사후 삭제 수단" |
| 사후 수단 | 직원·플랫폼 운영자가 **개별 첨부 삭제**(파일 삭제 + 메타 `deleted_at`) 가능. §4-3 "본문 지우기" 와 같은 예외 권한 |
| 파일명 정리 | 원본 이름은 **저장 경로에 쓰지 않는다**(경로는 uuid). `display_name` 은 `sanitizeDisplayName` 으로: 경로 구분자·제어문자·RTL 제어문자(U+202E 등) 제거, 길이 100자, 이중 확장자(`a.pdf.exe`)는 허용 목록 밖이면 어차피 거부. 원본 이름에 전화번호 등이 있을 수 있어 `detectPii(display_name)` 도 적용(걸리면 거부 대신 **이름을 `첨부N.확장자` 로 대체** 권장) |
| **EXIF 제거** | 사진(`jpg·png·webp`)에는 촬영 위치(GPS)·기기 정보가 들어갈 수 있다. **서버에서 재인코딩 또는 메타데이터 제거를 한다**(결정 #37 확정). 제거 라이브러리는 앱 의존성 추가이므로 **구현 때 별도 승인**을 받는다. 공용에는 넣지 않음(바이너리 처리·의존성을 공용에 들이지 않음). PDF 의 메타데이터는 제거하지 않음(한계 명시) |
| 자동 수집 금지 | 유지(앱 버전·화면 경로를 자동 첨부하지 않음) |

### 11-5. 보관 · 삭제
- **본문과 같은 기간**: 2층 해결 후 6개월에 본문 삭제 시 **첨부 파일도 함께 삭제**(§4-4). 메타 행은 통계용으로 `id·post_id·mime_type·byte_size·created_at·deleted_at` 만 남기고 `storage_path`·`display_name` 은 비운다(권장).
- **본문 지우기(예외)**: 글 본문을 `(삭제됨)` 으로 바꿀 때 그 글의 첨부도 **같은 트랜잭션 흐름에서 삭제**(파일 삭제는 DB 롤백이 안 되므로 순서: ① 메타에 삭제 표시 ② 파일 삭제 ③ 실패 시 정리 크론이 재시도).
- **고아 파일 정리**: 업로드는 됐는데 메타 행이 없는 파일(중간 실패)을 정리하는 크론이 필요. 앱 몫.
- **테넌트 해지·회사 삭제**: 해당 테넌트 경로 접두(`<tenant>/`) 전체 삭제를 해지 절차에 넣는다. 회사 삭제 시 표를 지워도 **스토리지 객체는 지워지지 않으므로** 회사 삭제 절차에서 파일 삭제 절차가 별도로 필요하다 → 앱 마이그 때 추가(범위 확대, 승인 필요).
- 보관 기간 숫자는 §4-4 와 같이 **확정 전 제안값**이며 [법무] 확인 대상.

### 11-6. 악성 파일 방어
| 계층 | 내용 |
|---|---|
| 허용 목록 | 확장자 + **매직 바이트** 둘 다 허용 목록에 맞아야 저장. 브라우저가 보낸 `Content-Type` 은 신뢰하지 않음 |
| 불일치 거부 | `.png` 인데 내용이 PE/ELF/HTML/스크립트면 `ATTACH_CONTENT_MISMATCH` |
| 실행 형식 금지 | 11-2 의 `BOARD_ATTACH_BLOCKED_EXT`. `svg`·`html`·`pdf` 안의 스크립트는 **내려받기 전용 + 앱 도메인과 분리된 서명 URL** 로 완화 |
| 크기·개수 | 서버·버킷·DB 세 곳에서 같은 값으로 제한(셋 중 하나가 뚫려도 막힘) |
| 바이러스 검사 | **하지 않음**(결정 #38 확정; 외부 서비스 도입 = 비용·위탁, Level 3) — 하지 않는 대신 "내려받기 전용·실행 형식 금지·직원/플랫폼 운영자만 열람" 으로 노출 범위를 좁힘. **이 한계를 계약에 적는다** |
| 남용 방어 | 업로드도 `RATE_LIMITED` 대상(분당·하루 업로드 수·총 용량, §9-4 수치에 더해 일 총량 상한 권장 50MB/사용자). 용량 폭증 방지 |
| 로그 | 거부 사유 코드만 남기고 파일 내용·원본 이름은 로그에 쓰지 않음 |

### 11-7. 드래그앤드롭 · 화면 몫
- 파일 선택 버튼 + 드래그앤드롭 영역 + 붙여넣기(스크린샷 Ctrl+V)는 **각 앱 화면 구현**이며 공용 계약에는 없다(공용은 화면 컴포넌트를 공유하지 않는다 — §1).
- 계약이 화면에 요구하는 것만 문서화: ① 허용 형식·개수·용량을 **업로드 전에 안내** ② 선택 즉시 클라이언트에서 같은 상수로 **사전 검사(편의용, 신뢰하지 않음)** ③ 개인정보 체크 ④ 실패 사유 코드별 문구 ⑤ 진행률·취소. 서버가 최종 판정.
- 공용이 `BOARD_ATTACH_*` 상수와 `validateAttachmentMeta` 를 내보내므로 세 앱 화면이 같은 수치를 쓰게 된다(안내 문구 불일치 방지).

### 11-8. 1층 첨부 허용 여부 — **결정됨: (가) 2층만, 1층 제외** (아래 표는 검토 기록)
| 선택지 | 내용 | 장단점 |
|---|---|---|
| **(가) 2층만 (확정)** | 첨부는 승격 대상인 기술 문의에만. 1층은 텍스트 | 일반 사용자(화주·차주·고객)가 개인정보 화면을 올릴 위험을 피함(§9-3 의 "일반 사용자에게는 더 위험" 판단 유지). 단, 2층은 **직원만** 쓰므로 "일반 사용자가 겪은 화면 오류" 사진은 직원이 대신 올리거나 말로 설명해야 함 |
| (나) 1층 직원만 | 직원이 1층에서도 첨부 가능, 승격 때 따라감 | 승격 흐름이 자연스러움. 일반 사용자 첨부는 여전히 없음 |
| (다) 1층 일반 사용자까지 | 일반 사용자도 첨부 | 저장 용량·악성 파일·개인정보 위험이 가장 큼. 화면 오류 설명에는 가장 편리. 이 경우 **일반 사용자용 한도를 낮춤**(예: 2개·3MB)과 11-4 체크를 강제 |

### 11-10. 법무 확인 항목 (파일 업로드) [법무]
1. 스크린샷·문서에 포함된 **제3자 개인정보**(고객·거래처·차주)가 플랫폼 운영자에게 전달·열람되는 것이 **제3자 제공/위탁**인지, 처리방침 항목 반영.
2. 업로드 사진의 **위치정보(GPS)** 등 EXIF 의 처리 — 제거하지 않을 경우의 고지.
3. 첨부 **보관 기간**(본문과 같게 할지)과 삭제 요청 대응 기한.
4. **저작권·불법 파일** 업로드에 대한 이용약관·책임 문구, 신고 시 삭제 절차.
5. **AI 위탁**: 장래 개발자 구독 Claude 가 2층 글을 분석할 때 **첨부(이미지·PDF)까지 읽는지**. 읽으면 이미지 속 개인정보가 AI 서비스로 처리·이전됨 → §9-7 의 AI 위탁 항목에 포함. **첨부는 분석 뷰에서 제외**(§5 의 `board_escalations_v` 에 첨부 경로·내용을 넣지 않음, 건수·형식만)를 권장.
6. ~~만 14세 미만 이용자의 사진 업로드 동의~~ → 1층 첨부가 제외(결정 #40)되어 **첨부에는 해당 없음**(일반 사용자 글쓰기 자체의 만 14세 문제는 §9-7 에 그대로).
- **[변호사]**: 업로드 콘텐츠에 대한 서비스 제공자의 책임 범위(이용약관 문구). **[세무사]**: 해당 없음.

**계약에 넣을 규칙 (결정 #47)**
1. **플랫폼 운영자(앱별 플랫폼 운영자 역할) 화면의 서버 코드는 1층 표를 `service_role` 로 읽지 않는다.** 스토리지 정책에 플랫폼 운영자 역할을 넣지 않으면 세션 클라이언트에서는 닫혀 있지만 `service_role` 은 RLS·스토리지 정책을 우회하므로, `/admin` 서버 코드가 `service_role` 로 1층을 읽으면 「플랫폼 운영자는 승격된 2층만」 원칙이 깨진다. 플랫폼 운영자 경로는 **2층 전용 RPC·뷰(`board_escalations_v`)만** 호출한다.
2. `service_role` 사용처는 ① 쓰기 RPC(`p_actor` 재검사, 결정 #28) ② 읽기 서명 URL 발급 **직전 권한 재확인 뒤**(2층 첨부 한정) ③ 정리 크론, 이 셋으로 한정하고 앱 코드 리뷰·시험 체크 항목에 넣는다(허용 목록).
3. 스토리지 정책에 플랫폼 운영자 역할을 넣지 않는다(플랫폼 운영자는 서명 URL 발급 경로로만 2층 첨부를 본다).
