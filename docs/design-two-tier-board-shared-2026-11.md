## 0. 한 줄 결론

1. 공용으로 뺄 가치가 있는 것은 **"계약과 순수 함수" 4가지뿐**이다: 분류 코드값, 상태 전이표(순수 함수), 개인정보 패턴 검사(순수 함수), 승격 규칙. 나머지(표·RLS·RPC·화면·알림·보관 정리)는 앱 몫이다. [근거: README 규칙 — 순수 함수·타입·계약만, DB·SQL·업무 규칙·비밀값 금지]
2. **세 앱의 DB와 로그인은 서로 분리돼 있어 "한 곳에서 모아 보기"는 앱 DB를 건드리지 않고는 불가능하다.** 현실적 안은 (A) 앱별 따로(권장 시작점)와 (B) 모아 보기(별도 수신 서비스 필요, 확장안)다. 3절.
3. 공용 버전은 **무태그 유지 방침과 별개로 새 서브패스 `./board` 하나를 추가하는 것**이라 새 태그가 필요하다(§6). 기존 서브패스·공개 API는 바뀌지 않는다.
4. 최소안은 "공용 계약 문서 + 코드값·전이표·패턴 검사 서브패스 1개"이고, 앱별 구현은 shipping 이 먼저(설계안 완성도가 가장 높음).

README 규칙을 기준으로 판정했다. "공용"은 `@platform/shared/board` 서브패스(순수 TypeScript, 부작용·네트워크·DB 없음) 후보다.

## 3. 플랫폼 운영자 계정과 통합 수신함

### 3-1. 현재 사실
- 계정은 **앱마다 따로**다. 세 앱의 로그인 사용자 표가 서로 다르고(`profiles`/`users`/`auth` 각각), 한 사람이 세 계정을 가진다 [확인: 위 표].
- 세 앱 DB 는 서로 분리돼 있다. 앱 간 연결은 ledgercore 와 wholesale·shipping 사이의 서명된 HTTP 호출(`@platform/shared/account`)과 SSO 뿐이며, 게시판 같은 데이터를 앱 간에 밀어 넣는 경로는 없다 [확인].
- shipping 은 이미 운영사별 푸시를 플랫폼 운영자(PLATFORM_ADMIN)에게 못 보낸다(구독 저장 DRIVER·ADMIN 만) [확인: shipping 설계안 §2]. wholesale·ledgercore 는 [미확인].

### 3-2. 두 가지 안

| | **A. 앱별 따로 (권장 시작점)** | **B. 모아 보기** |
|---|---|---|
| 구조 | 각 앱의 `/platform/board`(또는 ledgercore 의 관리 메뉴)에서 그 앱의 2층 글만 본다. 개발자는 앱 3곳에 각각 로그인 | 별도의 "수신 서비스"(새 앱 또는 새 Supabase 프로젝트)가 세 앱의 2층 글을 한 곳에 모은다 |
| 모으는 방법(하위 선택) | — | ① **밀어넣기**: 승격 시 앱 서버가 수신 서비스로 서명 호출(기존 `buildSignedCall` 방식 재사용 가능). 본문이 앱 밖으로 나가므로 개인정보 검사가 이중 필요 ② **끌어오기**: 수신 서비스가 앱별 읽기 전용 뷰를 주기 조회(§5 와 같은 구조, `ledger_sync_ro` 선례). 앱마다 읽기 전용 DB 계정·네트워크 허용이 필요 ③ **웹훅 알림만**: 수신함에는 "글 도착" 신호(id·앱·분류)만 오고 본문은 앱에서 본다 |
| 새로 필요한 것 | 없음(앱별 구현만) | 새 서비스 1개 + 앱↔서비스 계약(인증·재전송·중복 제거) + 서비스의 계정·감사·보관 정책 + 운영·배포 + 비밀값(서명 키·읽기 전용 계정 비밀번호) 관리 |
| 개발자 불편 | 앱 3곳을 돌아야 함 | 해소 |
| 개인정보 | 본문이 앱 안에 머묾(수탁 범위가 앱별로 단순) | ① 은 본문이 제3의 저장소로 복제됨 → **[법무]** 처리 위탁·보관 위치 재검토. ② 는 본문 복제 없이 조회만(권장), ③ 은 가장 안전 |
| 비용·위험 | 가장 낮음. 이미 세 앱이 각자 플랫폼 화면을 가졌거나 만들 예정 | **[추정]** 구현·시험 앱별 1~2일 + 서비스 구축 5일 이상, 이후 운영 비용(호스팅, 크론, 장애 대응). **새 서비스·새 인프라라 CLAUDE.md Level 3(구조·운영 복잡도)** → 개발자 승인 필수 |
| 되돌리기 | 쉬움(앱별 기능 스위치 끄기) | 서비스가 한 번 돌기 시작하면 데이터 이전·폐기 절차 필요 |

### 3-3. 권장
1. **시작은 A.** 앱별 2층 글 수신 화면만 만든다. 개발자 한 명이 하루 몇 번 열어 보는 규모에서 3곳 순회는 감당 가능하다 [추정, 예상 건수 미확인 → 결정 4].
2. **B 로 가는 길을 막지 않도록** 지금 정해 둘 것(비용 거의 없음): ① 분류·상태·시각 열을 세 앱이 같은 이름·값으로 둔다(§4, §5) ② 각 앱에 **2층 전용 읽기 전용 뷰**를 허용 가능하게 설계한다(승격된 글만) ③ 글 id 는 앱 안에서 유일하고, 모아 볼 때는 `(app_key, post_id)` 쌍으로 식별한다(`app_key` 값은 공용 상수: `MEAT`·`SHIP`·`LEDGER` 등 [결정 6]).
3. B 를 정말 원하면 **③(알림만) → ②(끌어오기)** 순으로 단계적으로, 새 서비스 없이 갈 수 있는지 먼저 본다: 예) 앱별 알림이 개발자 이메일·푸시로 오게 하면 "모아 보기" 요구의 상당 부분이 해소된다 [추정, 결정 4].
4. 앱 내부 플랫폼 운영자 계정은 **그대로 앱별**(wholesale `super_admin` allowlist, shipping `PLATFORM_ADMIN`, ledgercore 는 설계 중인 "관리" 메뉴). 이 설계를 이유로 계정 구조를 합치지 않는다.

## 4. 개인정보 · 보관 기간 공통 규칙

### 4-1. 코드값 (공용 상수 후보, 이 값은 shipping 설계안에서 가져와 재판단)
- 1층 분류(`tier=1`): `NOTICE`(공지) · `QUESTION`(문의) · `HANDOVER`(인수인계). 앱이 더 추가 가능하나 분석 조회 대상은 아님(1층 본문은 분석 제외, §5). 결정 7.
- 2층 분류(`tier=2`, 승격 시 선택): `BUG`(오류) · `FEATURE`(기능 요청) · `ACCOUNT`(계정·권한) · `ETC`(기타). **청구·계약 문의는 2층에 넣지 않는다**(shipping 설계안 §7-5, [변호사] 확인 전까지) [결정 8].
- 2층 상태: `RECEIVED` · `IN_PROGRESS` · `NEED_INFO` · `DONE` · `DECLINED`. 1층 글은 상태 `NONE`.
- 답글 가시성: `TENANT_ONLY`(직원 내부 메모) · `AUTHOR`(작성자에게 보이는 답) · `PLATFORM`(2층 답) — **개정으로 3값**(§9-2c). 아래 §5·§9-1 의 `TENANT_ONLY` 표현은 이 의미로 읽는다.
- 작성 측: `TENANT` · `PLATFORM`. 작성자 유형 `author_kind`(`STAFF`/`USER`)는 글·답글 모두 별도 열(§9-1, §9-6).

### 4-2. 전이표 (shipping 설계안 §6 을 공용화)
| 현재 | 다음 | 누가 |
|---|---|---|
| (1층 글) NONE | RECEIVED(승격) | TENANT(승격 권한자) — 한 방향, 되돌림 없음 |
| RECEIVED | IN_PROGRESS · NEED_INFO · DONE · DECLINED | PLATFORM |
| IN_PROGRESS | NEED_INFO · DONE · DECLINED | PLATFORM |
| NEED_INFO | RECEIVED | TENANT(답글로 보충) |
| DONE | RECEIVED(재오픈) | TENANT(승격 권한자), [결정 9] |
| DECLINED | — | 사유 필수. 재문의는 새 글 |
- `DECLINED`·`NEED_INFO` 로 갈 때 사유(답글) 필수 여부는 계약에 "필수"로 둔다.
- 순수 함수: `canTransition(from, to, actorSide)`, `requiresReason(to)`. DB 는 이 표를 `for update` + `ALREADY_PROCESSED` 로 강제(앱 몫).

## 5. 장래 읽기 전용 분석 조회의 공통 조건 (분석 기능은 만들지 않음)

선례: shipping `ledger_sync_ro`(읽기 전용 DB 계정, 열 단위 권한, RLS 정책) [확인: `ledger-sync-ro.md`]. 같은 모양으로 앱마다 **2층 전용 뷰**를 두면 장래 개발자 구독 Claude 가 주기적으로 읽기 전용 조회할 수 있다.

세 앱이 **같은 이름·값으로** 지켜야 할 조건(공용 계약 문서에 고정):
1. **뷰 이름·열**: `board_escalations_v` (이름은 [결정 6]에서 확정). 열: `app_key`, `post_id`, `tenant_id`(분석용 가명 id, 앱 안에서만 의미), `category`(§4-1 코드값), `escalation_status`(§4-1), `created_at`(1층 작성), `escalated_at`, `first_response_at`(첫 PLATFORM 답글), `closed_at`(DONE/DECLINED 시각), `updated_at`, `title`, `body`(§4-4 에 따라 삭제되면 null), `reply_count`.
2. **필터 가능**: `tier=2`(승격된 글만)이 뷰 조건. 1층 글은 뷰에 **행도 열도 없다** → 건수에도 안 잡힘(의뢰 조건).
3. **1층 본문 제외**: 뷰는 1층 `body`·1층 답글(`TENANT_ONLY`)을 아예 포함하지 않는다. 승격 때 넘기는 것은 본문+사유뿐(shipping 결정 12 권장안과 같음).
4. **시각은 모두 `timestamptz`(UTC)**. 처리 시간·응답 시간 분석이 가능해야 한다.
5. **분류는 고정 코드값**(자유 입력 금지). 코드 목록 버전을 계약에 적는다(`board_contract_version`).
6. **작성자 식별 제외**: 뷰에 작성자 id·이름·이메일 없음. 테넌트 이름 노출 여부는 [결정 3]에 따라 앱별로 가명 id 로 대체 가능.
7. **읽기 전용 계정**: 뷰 하나에만 `SELECT`, `INSERT/UPDATE/DELETE` 불가, 다른 표 접근 불가, 접속 허용 목록·사용 기록. 계정·비밀번호 관리는 앱 담당(비밀값은 저장소·문서·채팅 금지).
8. **개인정보**: 뷰에 올라오는 본문도 §4-3 패턴 거부를 거친 값이어야 한다. 본문 삭제(§4-4)가 뷰에 즉시 반영돼야 한다.
9. **계약 버전**: 열 추가는 하위 호환(분석 쪽이 모르는 열은 무시), 열 이름·값 변경은 계약 버전을 올린다.
- 이 설계에서 **만들지 않는 것**: 읽기 전용 계정 자체, 주기 조회 크론, 분석 로직, 요약·알림.

## 9. 보완: 일반 사용자 작성 · 3개 진입 · 스팸 · 경계 (2026-11-04 개정)

### 9-1. 작성자 유형과 가시 범위 (공용 계약)
- 새 열 `author_kind`(코드값): `STAFF`(운영사 직원: 대표·경리·일반 직원 등 테넌트 업무 권한자) · `USER`(테넌트 소속 일반 사용자). 기존 `author_side`(TENANT/PLATFORM, 답글 쪽 표시)와 별개다. `PLATFORM` 은 답글에만 있고 글의 `author_kind` 는 `STAFF`/`USER` 둘뿐.
- 공용 함수 `canView(post, viewer)`, `canReply`, `canEscalate`(계약용 순수 함수. 입력은 `viewerKind`(`STAFF`/`USER`/`PLATFORM`), `isAuthor`, `tier`):
  | 보는 사람 | 1층 글 | 1층 답글 | 2층 글(승격본) |
  |---|---|---|---|
  | `USER` | 자기가 쓴 글만 | 자기 글에 달린 답글만 | **안 보임**(승격 사실도 노출 안 함 [결정 14]) |
  | `STAFF` | 자기 테넌트 전부 | 전부 | 자기 테넌트가 올린 것 + 플랫폼 답변 |
  | `PLATFORM` | **안 보임(건수에도 없음)** | 안 보임 | 승격된 것만 |
- **승격 권한**: `STAFF` 중 앱이 "대표·경리급" 으로 판정한 사람만(`canEscalate` 는 앱이 넘기는 불리언 `hasEscalateRole` 을 받음. 역할 이름은 앱마다 달라 공용이 모름 — 본문 §1).
- 일반 사용자 글을 승격할 때 **작성자 유형·이름·연락처는 2층에 넘기지 않는다**(`author_kind` 도 넘기지 않음). 1층 대화(답글)도 안 넘기고 본문+승격 사유만(기존 권장 유지). 승격 시 운영사 직원이 본문을 **다시 읽고 편집 가능**하게 하는 안은 추가 [결정 15]: 일반 사용자가 쓴 본문이 개인정보를 가졌을 확률이 높으므로, 승격 직전 `detectPii` 재검사 + 체크 필수를 강제(§9-3).
- 답글 가시성 `TENANT_ONLY` 는 **일반 사용자에게도 보이는 답글**(그 글 작성자에게 보이는 직원 답)과 구분이 필요하다. 코드값 정리: 1층 답글은 `AUTHOR`(작성자에게 공개) · `TENANT_ONLY`(직원 메모, 일반 사용자에게 안 보임)로 나눈다 [결정 16, 이름은 §9-2c 로 통일]. `PLATFORM` 은 2층 답글 그대로.

### 9-2. 진입 3곳 코드 확인 (이음로지스 shipping, 읽기만)
| 진입 | 실제 | 비고 |
|---|---|---|
| 화주 화면 | 역할 `SHIPPER`, 홈 `/shipper`(`ROLE_HOME`) [확인] | **로그인 화주만.** |
| 차주 화면 | 역할 `DRIVER`, 홈 `/driver` [확인] | 카카오 가입·승인 후 |
| 운영사 대문 | `/t/<운영사코드>`(예 `/t/enc`, `app/t/[slug]/page.tsx`+`components/landing/Landing.tsx`), 로고·이름·[배송의뢰] [차주 가입] [앱 다운로드]·차주 로그인·**운영사 직원 로그인**·약관·개인정보 링크 [확인] | 개발자 설명과 일치(로그인·가입 링크가 있는 공개 진입 페이지) |

**[참고용 — 개정 2 로 대문 링크 안은 폐기, 진입은 화주·차주·직원 메뉴 3곳]** 아래는 개정 1 당시 코드 확인 기록으로, 사실(대문은 로그인 후 보이지 않음, 화주 대부분 계정 없음)만 유효하다. 개발자 해석("대문에서 쓰려면 로그인 뒤에만, 대문엔 문의하기 진입 링크와 필요시 공개 공지 읽기")과의 **차이 두 가지**:
1. **대문은 로그인한 사람에게는 보이지 않는다.** 코드가 `redirectIfSignedIn()` 으로 로그인·승인 대기·가입 전 모두 역할 홈/`/pending`/`/onboarding` 으로 보낸다 [확인: `Landing.tsx:10-18`, `t/[slug]/page.tsx`]. 즉 "대문에서 글쓰기" 는 **대문에 작성 폼을 두는 것이 아니라**, 비로그인 상태의 [문의하기] 링크 → 로그인 → 로그인 뒤 역할 홈의 게시판 메뉴로 가는 흐름이어야 한다. 진짜 작성 화면은 화주 홈·차주 홈·운영사 관리 화면 안에 있다 → 진입 3곳은 사실 **작성 화면 3개(화주/차주/직원)** + 대문의 로그인 유도 링크 1개.
2. **화주 대부분은 계정이 없다.** 대문의 [배송의뢰] 문구가 "가입 없이 바로 의뢰해요" 이고(`/o/<코드>` 비로그인 접수) 화주 로그인은 월정산 승급 등 일부 [확인: 대문 문구·`design-two-tier-board`·`ROLE_HOME`]. 따라서 "화주 화면에서 글을 쓴다" = **로그인한(승급한) 화주만 가능**하고, 비로그인 접수 화주는 게시판을 못 쓴다. 이 경계를 화면에서 분명히 안내해야 한다(접수 화주 문의는 기존 접수·운영사 전화 안내) [결정 17].
- 차주 쪽: 대문의 [차주 로그인] 은 `/t/<코드>/login`, 앱 설치 안내는 대문에 있음. 차주는 로그인 후 `/driver` 홈이므로 게시판 메뉴는 홈 안에 둔다.
- 공개 공지 읽기(비로그인): 이음로지스에 공지 기능 자체가 없다 [확인: 본문 shipping 설계안 §2]. 공개 공지는 이 설계 범위 밖 [결정 18 결정됨: 대문엔 아무것도 두지 않음].
- wholesale·ledgercore 대응(코드 미확인 부분 많음):
  - wholesale: 테넌트 안 일반 사용자 = **고객(retailer, 구매처)** 이 가장 가깝다 [추정, 근거: `wholesaler_retailers`·공급사별 고객 구조]. 공급사 조직 직원은 `STAFF`. 대문에 해당하는 공개 진입은 **공급사 미니샵/랜딩**(`wholesaler-tenant-landing-design.md` 존재) [확인: 파일명만, 본문 미확인]. 고객은 로그인 사용자 [추정].
  - ledgercore: **일반 사용자 역할이 없다** — 회사 구성원(소유자·회계담당·승인자·조회, 사용자 정의 역할)뿐이고 공개 가입도 없다 [확인: `design-platform-admin.md`]. `viewer`(조회) 역할이 USER 에 가장 가깝지만 이는 회사 직원이다. **→ ledgercore 는 `USER` 유형 없음. `STAFF` 만 쓰는 1층**으로 시작하는 것을 권장. 외부(SSO 연동) 사용자의 게시판 진입은 [미확인].
  - 공용 계약은 `USER` 를 **선택 사항**으로 둔다(앱이 일반 사용자 개념이 없으면 `author_kind=STAFF` 만 허용).

| 읽기 전용 뷰 | 선례 `ledger_sync_ro`(뷰·명시 GRANT). **마이그 321 규칙: 새 public 표는 같은 마이그에서 GRANT** 를 지킬 것. 역할 생성·마이그 적용은 개발자 승인 | `platform_audit` 패턴 재사용 가능 |

- 이에 따라 **ledgercore 는 `USER` 없이 `STAFF` 만, 알림 없이 화면 배지만, 2층은 장터 회사 승인 뒤**로 최소안을 잡는다. 앞 §6-1 의 ledgercore 마지막 순서가 더 굳어진다.
- 공용 계약에 추가: 앱이 지원하는 능력을 선언하는 플래그 `supports: { user: boolean, notify: boolean }` 같은 **능력 선언은 문서로만** 두고 코드 상수는 늘리지 않는다 [결정 24].
- wholesale 의 고객(`retailer`)은 현재 문의 화면이 없으므로 `USER` 작성 화면은 **신규 화면**이다. 고객은 `/shop` 등 공급사별로 연결된 거래처이므로 글은 **(공급사, 고객) 쌍**에 묶인다 [추정, 결정 25: 고객 1곳의 여러 공급사 중 어느 공급사 테넌트 글로 저장할지 = 현재 화면의 공급사].

### 9-2c. shipping 대조 결과 반영 (shipping-prj-22)
- **일치**: 분류·상태 코드값, 글 길이(100/2000/200), 전이표는 사실상 일치. 공용안 채택 차이: `DECLINED` 는 종결, 사유 필수는 `DECLINED`·`NEED_INFO`, 뷰 열 `first_response_at`·`reply_count`·`app_key('SHIP')` 추가, `detectPii` 이메일 패턴 포함.
- **작성자 종류는 앱이 정의**한다. 공용 계약은 두 겹으로 둔다: ① `author_kind` = `STAFF` · `USER`(공용, §9-1) ② `author_role` = 앱 정의 하위 구분(문자열, 공용은 형식만 규정: 영문 대문자·밑줄 32자 이하). shipping = `SHIPPER` / `DRIVER` / `STAFF`, wholesale = `RETAILER` / `OWNER` / `MANAGER` / `STAFF`, ledgercore = `STAFF` 계열만. 분석 뷰에는 둘 다 넣지 않는다(§9-6).
- **분류는 작성자 종류별 허용 목록**: `NOTICE`·`HANDOVER` 는 `STAFF` 전용, `USER` 는 `QUESTION` 과 (선택) `SUGGESTION` 만. 허용 목록 표는 공용 상수 `ALLOWED_CATEGORIES_BY_KIND`.
- **답글 가시성은 shipping 이 이미 쓰는 이름으로 통일**(변경 최소): `TENANT_ONLY`(직원 내부 메모) · `AUTHOR`(작성자에게 보이는 답) · `PLATFORM`(2층 답, 직원만 보고 일반 사용자에겐 안 보임). 앞 §9-1·§9-6 의 `STAFF_ONLY`/`VISIBLE_TO_AUTHOR` 는 이 이름으로 읽는다 (`STAFF_ONLY`→`TENANT_ONLY`, `VISIBLE_TO_AUTHOR`→`AUTHOR`).
- **작성 대상 테넌트는 화면에서 고른 값으로 고정**하는 규칙을 공용 계약에 넣는다. 이유: 차주는 운영사 여럿에 속할 수 있고 shipping 의 `current_tenant_id()` 는 DRIVER 에게 null 이라 차주용 RPC 가 별도로 필요하다. 규칙: `tenant_id` 는 호출 인자로 받되 서버가 (사용자, 테넌트) 소속을 검증, 소속 아니면 `NOT_VISIBLE`. wholesale 고객도 같은 규칙(현재 보는 공급사).
- **쓰기 경로 충돌(실제 충돌 1곳)**: 공용안은 "서버가 저장 전에 `detectPii`" 인데 shipping RPC 는 `authenticated` 에 직접 열려 있어 우회할 수 있다. 계약 문구(안):
  > **글·답글을 저장하는 유일한 경로는 서버 액션이다.** 쓰기 RPC 는 `service_role` 전용으로 하고 서버 액션만 호출한다. 서버 액션은 (1) 세션에서 사용자·역할 확인 (2) `detectPii`·길이·분류 허용 목록·작성 제한 검사 (3) RPC 에 `p_actor`(사용자 id)와 `tenant_id` 를 넘긴다. RPC 는 서비스 키만 믿지 않고 **DB 안에서 `p_actor` 의 테넌트 소속과 권한을 다시 검사**한다(account `platform_*` 의 이중 방어 패턴). 읽기 RPC 는 `authenticated` 로 열어도 되나 반환은 가시 범위(§9-1)를 DB 안에서 강제한다.
  - 대안 (나): 같은 정규식을 SQL 에도 구현 — 두 구현이 어긋날 위험이 크고 SQL 정규식 유지 부담이 있어 비권장. 공용 시험 벡터 대조로 어긋남을 잡을 수는 있다.
  - 권장 (가). 대가: 서버 액션이 곧 보안 경계라 `p_actor` 를 위조하지 못하도록 서버 코드 검토가 필요. [결정 28]
- **계약 변경 비용**: 앱 핀(shipping `#v0.3.0-rc.3`)을 올려야 하고 CHECK·뷰를 재정렬해야 하므로 **앱이 마이그를 쓰기 전에 `board_contract_version` 을 확정**해야 한다 → 공용 `./board` 첫 태그와 계약 v1 을 함께 확정한 뒤 앱 마이그 작성(§6-1 순서 1→2 를 엄격히). 계약 v1 이 바뀌면 앱 마이그가 어긋나므로 확정 전 앱 마이그 작성 금지.
- **남용 방지 추가**: 사용자별 레이트 제한 + **열린 글 상한**(미해결 글 N건 초과 시 새 글 거부, 직원 답 후 다시 가능) [결정 19 에 포함].
- **알림**(앱 몫, 공용은 이벤트 이름만 문서화): 이벤트 `POST_CREATED`(직원에게) · `AUTHOR_REPLIED`(작성자에게) · `ESCALATED_RECEIVED`(플랫폼) · `PLATFORM_REPLIED`(직원). shipping: 직원 새 글 알림 대상은 대표·경리만(`ops_notify` 재사용) [결정 29 결정됨], 작성자 답 알림은 차주 푸시 가능·화주 앱 안 알림만. wholesale: 대표·매니저 알림함 선례. ledgercore: 알림 없음, 배지만.
- **차주 PENDING(소속 승인 전) 작성: 불허 [결정 30 결정됨]** — 소속이 확정되지 않은 사용자가 테넌트 직원에게 글을 올리게 하면 스팸·개인정보 경로가 되고, 승인 문의는 기존 가입 안내로 충분].
- **진입 위치 (개정 2 로 최종)**: **대문에는 링크를 두지 않는다**(대문 변경·시험·링크 위치·로그인 복귀 처리 논의 모두 범위에서 삭제). 진입점은 3곳뿐: 화주 = `shipperLinks` 「문의」 항목+기능 스위치, 차주 = 하단 탭 증설 대신 「내 정보」 안이나 상단바, 운영사 직원 = 관리자 메뉴. 비로그인 화주 문의는 기존 발주 문의 유지(§9-2d). (앞 §9-2 의 대문 코드 확인 결과는 이제 참고 사실일 뿐이며, 작은 링크 안은 폐기)

### 9-2d. 비로그인 화주 A안: 발주 문의를 직원 1층 수신함에 함께 보이기 (shipping 기준)
- 결정: **기존 `order_inquiries` 를 그대로 유지**하고, 직원 수신함에서 게시판 1층 글과 **함께 보이게만** 한다. 답은 전화·문자(게시판 답글 없음). 새 익명 글쓰기·새 공개 입구 없음. 화주 접수 화면의 「전화번호 남기기」 카드(`/o/<코드>`)도 변경 없음.
- 현재 구조(읽음) [확인: 마이그 `20261101195000`, `design-order-inquiry-2026-10.md`]: 표 `order_inquiries`(`tenant_id`, `phone`, `memo`≤200, `status` NEW/CONTACTED/CONVERTED/DROPPED, `inquiry_count`, `created_at`, `last_inquired_at`, `handled_by/at`, `order_id`), 닫힌 표+RPC(`admin_list_order_inquiries(p_status,p_limit)` 등), 목록 화면 `/admin/inquiries`, 메뉴 배지 `LivePendingBadge`(NEW 건수), 보관 정리 `cleanup_order_inquiries(p_days default 30)`.
- **합산 방식(권장 = 읽기 전용 합산, 표 합치지 않음)**: 직원용 읽기 RPC 하나(예: `admin_list_inbox(p_limit)`, 이름 임시)가 **두 원천을 `union all`** 해 공통 모양으로 돌려준다 — `(source = BOARD | ORDER_INQUIRY, id, 요약(제목 또는 "발주 문의 · 전화번호 앞자리 가림 안 함"), 작성자 표시, created_at, 원천 상태)`. 상태는 **원천별 상태를 그대로** 표시하고 통합 상태값을 새로 만들지 않는다(전이표가 다름). 항목을 열면 BOARD 는 게시판 상세, ORDER_INQUIRY 는 **기존 `/admin/inquiries` 상세·버튼**(전화함·종료·주문으로 만들기)으로 이동 → 처리 로직 재사용, 중복 구현 없음.
- 영향 범위(shipping):
  | 항목 | 영향 |
  |---|---|
  | `order_inquiries` 표·기존 RPC | **변경 없음**(읽기 합산만) |
  | 신규 | 합산 RPC 1개 + 수신함 화면(또는 기존 목록 위에 게시판 항목 섞기) + 배지 건수 합산(`LivePendingBadge` 의 `inquiries` 에 게시판 새 글 건수 더하기 — 기존 배지 API 응답 모양 변경 여부 확인 필요) |
  | 공용(`@platform/shared`) | **영향 없음** — 발주 문의는 공용 계약 밖(앱 고유). 합산 뷰는 공용 계약에 넣지 않는다 |
  | 개인정보 | 발주 문의의 전화번호는 직원 전용 화면에 이미 전체 표시됨 [확인: 설계 결정 6 기본]. 합산 뷰도 **직원 전용**(`require_staff_role`, 자기 운영사) — 플랫폼 운영자·2층 분석 뷰·읽기 전용 계정에는 **포함하지 않는다**(전화번호가 들어 있으므로) |
  | 보관 | 발주 문의는 기존 정리(30일 등, `cleanup_order_inquiries`) 유지. 게시판 보관 기간과 별개(합치지 않음) [법무 참고: 일반 사용자 글과 보관 기간이 다름] |
  | 승격 | 발주 문의는 **2층으로 승격 못 함**(주문 문의이지 기술 문제가 아님). 수신함 목록에서도 승격 버튼은 BOARD 항목에만 |
  | 열림·정렬 | 시각 기준 합산 정렬. 읽음 표시는 앱이 정함 |
  | **처리 필요 건수(배지) — 결정 33 확정** | 정의 = **「직원 답을 기다리는 건」**. 구성: ① 신규 발주 문의(`NEW`, 아직 전화하지 않은 건) ② 직원이 아직 답하지 않은 1층 글 ③ 직원이 답한 뒤 작성자가 다시 쓴 1층 글(**마지막 답글의 작성자가 직원이 아닌 경우**). 합산 수신함 목록의 「처리 필요」 필터와 메뉴 배지가 같은 정의를 쓴다(`CONTACTED`·`CONVERTED`·`DROPPED` 발주 문의, 직원이 마지막으로 답한 글, 종료·숨김 글은 제외). 판정은 **답글의 작성자 유형 열**(`author_kind`, §9-1)로 한다 → **공용 계약: 답글도 `author_kind`(STAFF/USER) 열을 가진다**(글과 같은 값, 답글 `author_side` TENANT/PLATFORM 과 별개). 2층 글은 이 건수에 포함하지 않는다(직원이 아니라 플랫폼이 답할 차례) |
  | 시험 | 격리(타 운영사 문의가 합산에 안 섞임), 비직원 호출 거부, 플랫폼 운영자 호출 거부, 원천별 건수 합과 배지 일치 |
- 다른 앱: **wholesale 해당 없음**(비로그인 접수 문의 기능 없음 — 고객은 로그인 사용자, 현재 문의 화면도 없음), **ledgercore 해당 없음**(공개 접수·일반 사용자 없음). 둘은 1층 수신함이 게시판만으로 구성된다.
- 대안(비권장): 발주 문의를 게시판 글로 변환·복사 — 전화번호가 본문(`detectPii` 대상)에 들어가 거부되며 표·상태 이중화 위험.

### 9-4. 스팸 · 도배 제한
- **익명 작성 금지**(결정 반영): 로그인한 `user_id` 가 없는 작성은 허용하지 않는다. 대문에는 게시판 링크도 두지 않는다(개정 2).
- 사용자별 작성 제한은 **필요하다**(일반 사용자 풀은 외부 대중에 가깝고 계정 생성이 쉬움): 공용 계약에 **기본값 제안**을 명시하고 값은 앱 설정으로 둔다.
  - 일반 사용자: 하루 글 N건(예 5), 분당 1건, 같은 내용 반복 거부(해시 비교는 앱), 미승인(승인 대기) 계정은 작성 불가.
  - 직원: 완화(예 하루 30건) — 도배보다 실수 방지 목적.
  - 한도 초과 오류 코드값: `RATE_LIMITED`. 공용은 **상수와 판단 함수 `exceedsLimit(counts, kind)` 정도**만(카운트 조회는 DB 라 앱 몫).
- 제한 대상 수치는 [결정 19]. 시행 위치는 서버 RPC(클라이언트 제한은 무의미).
- 정지·탈퇴 사용자: 새 글 불가, 기존 글은 직원이 열람(테넌트 업무 기록) — 탈퇴 시 본문 처리는 [법무] 개인정보 보관 규정과 연동.
- 직원 신고·차단: 직원이 특정 일반 사용자의 작성 권한을 막는 기능은 **확장안**(최소안은 "숨김"만).

### 9-5. 기존 분쟁 · 발주 문의와 경계 (문구)
공용 상수 `BOARD_SCOPE_NOTICE`(작성 폼 위 안내, 앱이 한글로 다듬음) 초안:
> 이 게시판은 **일반 문의와 안내** 용도입니다. 주문·배송·금액에 관한 문제는 해당 주문 화면의 **분쟁(문의) 기능**을, 접수 전 문의는 **발주 문의**를 이용해 주세요. 주문 번호와 금액 확인이 필요한 일은 게시판에 쓰지 마세요.
- 이음로지스 기존 기능: 분쟁 `disputes`(주문에 묶임, 화주·차주 개설), 발주 문의 `order_inquiries`(비로그인 화주 발주 문의) [확인: shipping 설계안 §2]. 게시판은 이 둘과 **표·화면·알림을 공유하지 않는다**.
- 앱이 분류 `ORDER_RELATED`(안내 전용)를 둘지: 작성 중 이 분류를 고르면 저장하지 않고 안내 문구로 보내는 방식도 가능하나, 코드값은 늘리지 않는다 [결정 20, 권장 안 함].
- wholesale·ledgercore 의 기존 대응 기능(분쟁·문의 화면)은 [미확인].

## 11. 첨부 파일 (2026-11-04 개발자 결정으로 추가 — 이 절이 §4-3·§6-3·§9-3·§9-7 의 "첨부 없음" 을 뒤집는다)

**개발자 결정(11-04)**: 2층 게시판은 첨부 파일 업로드를 지원한다. 드래그앤드롭이면 더 좋다. 결정 #34~#45 는 **모두 권장대로 확정**됐다(§11-11). 이 절의 표·상수는 확정값이며, 미확정은 사전 확인 3건뿐이다. 구현·코드·커밋·push·태그 없음.

### 11-1. 한눈에
- 첨부는 **2층(기술 문의)에만** 있다. **1층은 첨부 불가**(결정 #40, 확정).
- 파일은 **앱별 비공개 버킷**에 두고, 열람은 **짧은 서명 URL**로만 한다. 업로드는 **서버를 거친다**(브라우저가 스토리지에 직접 올리지 않음).
- 공용(`@platform/shared/board`)은 **상수와 순수 검사 함수만** 둔다(파일 바이트를 저장·전송하지 않음, 비밀·SQL 없음 — README 원칙 유지). 저장·권한·정리는 앱 몫. **드래그앤드롭은 화면 몫**이라 공용 계약에 없다.
- 개인정보: 스크린샷·문서는 `detectPii` 로 못 거른다 → 사람이 확인하는 체크(11-4)와 EXIF 제거로 보완하고, 한계를 계약에 명시한다.

### 11-2. 계약 (공용 후보, `board_contract_version` v1 에 포함 — 결정 #34)
**첨부 메타 열(앱이 `board_attachments` 표로 둠, 글 본문 표에는 열을 추가하지 않음)**
| 열 | 내용 |
|---|---|
| `id` | uuid |
| `post_id` | 2층 글 id (답글 첨부도 허용 — 결정 #35 확정, 아래 `reply_id`) |
| `reply_id` | 선택. 답글에 붙인 경우 |
| `storage_path` | 버킷 안 경로. **서버가 만든 값만**: `<tenant>/<post_id>/<uuid>.<확장자>` (원본 파일명을 경로에 쓰지 않음) |
| `display_name` | 화면 표시용 정리된 이름(11-4). 원본 이름은 저장하지 않는 것을 권장 |
| `mime_type` | 서버가 **매직 바이트로 판정한** 값(브라우저가 보낸 Content-Type 아님) |
| `byte_size` | 서버가 확인한 크기 |
| `sha256` | (선택) 중복·변조 확인용. 최소안에서는 생략 가능 |
| `uploaded_by_kind` | `STAFF`/`USER` (§9-1 과 같은 의미) — 작성자 이름은 2층 뷰에 안 나감. 2층은 직원만 쓰므로 실제 값은 `STAFF` |
| `privacy_confirmed_by`·`privacy_confirmed_at` | 「개인정보 가림 확인」 체크를 한 사람과 시각(결정 #43, 서버가 기록; 이름은 2층 뷰에 안 나감) |
| `created_at` | timestamptz |
| `deleted_at` | 본문 지우기·정리 크론이 파일을 지운 시각(행은 남기고 파일만 삭제 가능) |

**상수 (코드 상수 = 공용, 값은 결정 #36·#39·#42 로 확정)**
| 상수 | 확정값 | 비고 |
|---|---|---|
| `BOARD_ATTACH_MAX_COUNT` | 글(또는 답글) 1건당 **5개** | 앱이 DB 에서 다시 센다 |
| `BOARD_ATTACH_MAX_BYTES` | 파일 1개 **4MB** (결정 #48 로 5MB → 4MB 갱신, 확정) | 서버 경유 업로드가 요청 본문 한도(약 4.5MB 추정)에 걸리지 않게 함. 선례: wholesale·ledgercore 4MB 서버 경유 |
| `BOARD_ATTACH_MAX_TOTAL_BYTES` | 건당 합계 **15MB** | 비용 상한 |
| `BOARD_ATTACH_ALLOWED` | 이미지 `jpg·png·webp`, 문서 `pdf`, 텍스트 `txt·log`(오류 로그용) | **허용 목록 방식**(금지 목록 아님). `heic` 는 브라우저에서 못 보여 제외 권장. 동영상·압축파일·오피스 파일(`docx·xlsx`, 매크로 위험)은 최소안에서 제외 |
| `BOARD_ATTACH_BLOCKED_EXT` | 실행·스크립트·압축 형식 일체(`exe·bat·cmd·ps1·sh·js·vbs·msi·dll·jar·apk·scr·com·html·htm·svg·zip·7z·rar` 등) | 허용 목록 밖은 어차피 거부이므로 **이중 안전망**. 특히 `svg`·`html` 은 스크립트가 들어갈 수 있어 이미지로 취급하지 않음 |
| `BOARD_ATTACH_NAME_MAX` | 표시 이름 100자 | |

**공용 순수 함수 후보**: `validateAttachmentMeta({name, size, declaredMime, head})` — 이름·크기·확장자·**앞부분 바이트(매직 바이트)** 를 받아 허용 여부와 판정 형식을 돌려줌(파일 전체를 받지 않음; 선례: shipping `lib/storage/magic`·`readDocHead` 가 앞 1KB 만 Range 로 읽음). `sanitizeDisplayName(name)`. `exceedsAttachLimit(count, totalBytes)`. 시험 벡터는 `__vectors__/attachments.json`(허용·거부·이중확장자·가짜 확장자 등).

**오류 코드 후보(추가)**: `ATTACH_TOO_MANY`, `ATTACH_TOO_LARGE`, `ATTACH_TYPE_NOT_ALLOWED`, `ATTACH_CONTENT_MISMATCH`(확장자와 내용 불일치), `ATTACH_NAME_INVALID`, `ATTACH_NOT_FOUND`, `ATTACH_PRIVACY_NOT_CONFIRMED`(11-4 체크 누락), 기존 `NOT_VISIBLE`·`RATE_LIMITED` 재사용.

| 승격 시 | 1층에는 첨부가 없으므로(결정 #40) 승격으로 넘어오는 첨부도 없다. 직원이 **승격 뒤 2층에서** 첨부를 올린다 | 앱 |

| 대책 | 내용 |
|---|---|
| **「개인정보 가림 확인」 체크(필수)** | 업로드(또는 글 등록·승격) 때 "첨부에 이름·연락처·주소·계좌·차량번호·고객 정보가 보이지 않음을 확인했습니다" 체크 필요. 서버가 체크 값을 요구(`ATTACH_PRIVACY_NOT_CONFIRMED`). 글 1건당 1회 체크(파일마다 반복하지 않음, 결정 #43). **서버가 강제하고 확인한 사람·시각을 기록**(`privacy_confirmed_by`·`privacy_confirmed_at`). 최종 책임은 테넌트(§4-3 승격 확인과 같은 구조). 체크 문구는 공용 상수 후보 |
| 작성 안내 | 첨부 영역에 상시 문구: "화면 캡처에서 개인정보·거래처 정보는 가려서 올려 주세요" + `detectPii` 가 첨부에는 **작동하지 않음**을 계약에 명시 |
| 한계 | 이미지 속 글자는 못 거른다(OCR 은 하지 않음 — 비용·오탐·새 위탁 발생, 하지 않기를 권장). 따라서 "차단"이 아니라 "확인 절차 + 사후 삭제 수단" |
| 사후 수단 | 직원·플랫폼 운영자가 **개별 첨부 삭제**(파일 삭제 + 메타 `deleted_at`) 가능. §4-3 "본문 지우기" 와 같은 예외 권한 |
| 파일명 정리 | 원본 이름은 **저장 경로에 쓰지 않는다**(경로는 uuid). `display_name` 은 `sanitizeDisplayName` 으로: 경로 구분자·제어문자·RTL 제어문자(U+202E 등) 제거, 길이 100자, 이중 확장자(`a.pdf.exe`)는 허용 목록 밖이면 어차피 거부. 원본 이름에 전화번호 등이 있을 수 있어 `detectPii(display_name)` 도 적용(걸리면 거부 대신 **이름을 `첨부N.확장자` 로 대체** 권장) |
| **EXIF 제거** | 사진(`jpg·png·webp`)에는 촬영 위치(GPS)·기기 정보가 들어갈 수 있다. **서버에서 재인코딩 또는 메타데이터 제거를 한다**(결정 #37 확정). 제거 라이브러리는 앱 의존성 추가이므로 **구현 때 별도 승인**을 받는다. 공용에는 넣지 않음(바이너리 처리·의존성을 공용에 들이지 않음). PDF 의 메타데이터는 제거하지 않음(한계 명시) |
| 자동 수집 금지 | 유지(앱 버전·화면 경로를 자동 첨부하지 않음) |

### 11-5. 보관 · 삭제
- **본문과 같은 기간**: 2층 해결 후 6개월에 본문 삭제 시 **첨부 파일도 함께 삭제**(§4-4). 메타 행은 통계용으로 `id·post_id·mime_type·byte_size·created_at·deleted_at` 만 남기고 `storage_path`·`display_name` 은 비운다(권장).
- **본문 지우기(예외)**: 글 본문을 `(삭제됨)` 으로 바꿀 때 그 글의 첨부도 **같은 트랜잭션 흐름에서 삭제**(파일 삭제는 DB 롤백이 안 되므로 순서: ① 메타에 삭제 표시 ② 파일 삭제 ③ 실패 시 정리 크론이 재시도).
- **고아 파일 정리**: 업로드는 됐는데 메타 행이 없는 파일(중간 실패)을 정리하는 크론이 필요(선례: shipping `clean-driver-docs`, wholesale `purge-expired-personal-data`). 앱 몫.
- **테넌트 해지·회사 삭제**: 해당 테넌트 경로 접두(`<tenant>/`) 전체 삭제를 해지 절차에 넣는다. ledgercore 는 결정 #26(설정성 표 분류) 때문에 **스토리지 객체는 표 삭제로 지워지지 않으므로** `platform_delete_tenant` 에서 파일 삭제 절차가 별도로 필요하다 → 앱 마이그 때 추가(범위 확대, 승인 필요).
- 보관 기간 숫자는 §4-4 와 같이 **확정 전 제안값**이며 [법무] 확인 대상.

### 11-6. 악성 파일 방어
| 계층 | 내용 |
|---|---|
| 허용 목록 | 확장자 + **매직 바이트** 둘 다 허용 목록에 맞아야 저장. 브라우저가 보낸 `Content-Type` 은 신뢰하지 않음 |
| 불일치 거부 | `.png` 인데 내용이 PE/ELF/HTML/스크립트면 `ATTACH_CONTENT_MISMATCH` |
| 실행 형식 금지 | 11-2 의 `BOARD_ATTACH_BLOCKED_EXT`. `svg`·`html`·`pdf` 안의 스크립트는 **내려받기 전용 + 앱 도메인과 분리된 서명 URL** 로 완화 |
| 크기·개수 | 서버·버킷·DB 세 곳에서 같은 값으로 제한(셋 중 하나가 뚫려도 막힘) |
| 바이러스 검사 | **하지 않음**(결정 #38 확정; 외부 서비스 도입 = 비용·위탁, Level 3) — 하지 않는 대신 "내려받기 전용·실행 형식 금지·직원/플랫폼 운영자만 열람" 으로 노출 범위를 좁힘. **이 한계를 계약에 적는다** |
| 남용 방어 | 업로드도 `RATE_LIMITED` 대상(분당·하루 업로드 수·총 용량, §9-4 수치에 더해 일 총량 상한 권장 50MB/사용자). 용량 폭증 방지 |
| 로그 | 거부 사유 코드만 남기고 파일 내용·원본 이름은 로그에 쓰지 않음 |

### 11-7. 드래그앤드롭 · 화면 몫
- 파일 선택 버튼 + 드래그앤드롭 영역 + 붙여넣기(스크린샷 Ctrl+V)는 **각 앱 화면 구현**이며 공용 계약에는 없다(공용은 화면 컴포넌트를 공유하지 않는다 — §1).
- 계약이 화면에 요구하는 것만 문서화: ① 허용 형식·개수·용량을 **업로드 전에 안내** ② 선택 즉시 클라이언트에서 같은 상수로 **사전 검사(편의용, 신뢰하지 않음)** ③ 개인정보 체크 ④ 실패 사유 코드별 문구 ⑤ 진행률·취소. 서버가 최종 판정.
- 공용이 `BOARD_ATTACH_*` 상수와 `validateAttachmentMeta` 를 내보내므로 세 앱 화면이 같은 수치를 쓰게 된다(안내 문구 불일치 방지).

### 11-8. 1층 첨부 허용 여부 — **결정됨: (가) 2층만, 1층 제외** (아래 표는 검토 기록)
| 선택지 | 내용 | 장단점 |
|---|---|---|
| **(가) 2층만 (확정)** | 첨부는 승격 대상인 기술 문의에만. 1층은 텍스트 | 일반 사용자(화주·차주·고객)가 개인정보 화면을 올릴 위험을 피함(§9-3 의 "일반 사용자에게는 더 위험" 판단 유지). 단, 2층은 **직원만** 쓰므로 "일반 사용자가 겪은 화면 오류" 사진은 직원이 대신 올리거나 말로 설명해야 함 |
| (나) 1층 직원만 | 직원이 1층에서도 첨부 가능, 승격 때 따라감 | 승격 흐름이 자연스러움. 일반 사용자 첨부는 여전히 없음 |
| (다) 1층 일반 사용자까지 | 일반 사용자도 첨부 | 저장 용량·악성 파일·개인정보 위험이 가장 큼. 화면 오류 설명에는 가장 편리. 이 경우 **일반 사용자용 한도를 낮춤**(예: 2개·3MB)과 11-4 체크를 강제 |

- **[확인] 설정**: account `next.config.mjs` → `serverActions.bodySizeLimit: '4.5mb'`, wholesale → `'8mb'`, shipping → **설정 없음(Next 기본 1MB)**.
- **[추정·미확인] 호스팅 한도**: Vercel 서버리스 함수 요청 본문 약 4.5MB. wholesale 은 Vercel 사용 흔적이 있으나(STATE) account·shipping 의 호스팅은 **[미확인]**. 한도 값은 공식 문서·실업로드로 확인해야 한다. 4.5MB 가 맞다면 wholesale 의 `8mb` 설정도 실제로는 4.5MB 에서 막힌다.
- **[확인] 선례**: wholesale 는 서버 액션 업로드 + 4MB 상한(`supplier-auth.ts` `.upload(path, buffer…)`, 마이그 206 버킷 4MB). shipping 은 서류·증빙을 **브라우저 직접 업로드**(스토리지 `authenticated` INSERT 정책 + 서버가 업로드 후 앞 1KB 로 매직 바이트 확인, 10MB 상한). **서명 업로드 URL(`createSignedUploadUrl`)을 쓰는 선례는 세 앱에 없다**(검색 결과 0건).
- **[확인] ledgercore 선례(캡틴 전달 + 코드 대조)**: 증빙 업로드는 `app/ledger/_screens/evidence.tsx` 의 **서버 액션**이 `FormData` 를 받아 **사용자 세션 클라이언트(RLS)** 로 스토리지에 저장한다(`c.supabase.storage…upload`, 파일 4MB 상한, SHA-256 기록, 기록 실패 시 고아 파일 삭제, 열람은 서명 URL 60초). 즉 ledgercore 는 **서버 경유 + 4MB** 가 이미 동작하는 선례다. 캡틴 전달은 "4.5MB 한도 때문에 서버 경유 불가"였으나, **코드로는 4MB 서버 경유가 가능하다는 쪽이 맞다** — 한도 때문에 못 하는 것은 **5MB** 다. 따라서 이 사실은 (나)의 근거가 아니라 **(가) 파일당 4MB 의 근거**를 강화한다(세 앱 중 wholesale·ledgercore 둘이 이미 4MB 서버 경유).

**확정: (가) 서버 경유 + 파일당 상한 4MB, 파일은 요청 1건에 1개씩.** (검토 당시 권장이 그대로 채택됨)
- 이유: ① 스토리지 선제 검사 원칙과 선례(wholesale)가 그대로 맞는다 ② 격리 구간·미확정 정리·토큰 위험이 아예 없다 ③ 공용 계약이 작다 ④ 스크린샷·로그·PDF 용도에 4MB 는 대체로 충분하고(wholesale 도 4MB), 합계 15MB·건당 5개는 요청을 여러 번 보내 그대로 지킬 수 있다.
- 조건: 호스팅 요청 본문 한도(약 4.5MB 추정)를 **실업로드로 확인**해 4MB(+오버헤드) 가 통과해야 한다. 통과하지 못하면 상한을 더 낮추는 것을 개발자가 재결정한다((나) 전환은 채택하지 않은 안, 필요 시에만 재논의).
- **(참고) (나)를 검토해야 했을 경우**: 개발자가 5MB 이상을 꼭 원하거나, 한도 확인에서 4MB 도 못 넘을 때. 이때는 구현량·시험 비용이 크게 늘고 선례가 없다는 점을 감수한다.
- **결정 #36 과의 충돌은 해소됨**: 개발자가 #48 로 **파일당 5MB → 4MB** 를 재결정했다(합계 15MB·5개 유지, #36 갱신).
- 남은 조건: 호스팅 요청 본문 한도(약 4.5MB 추정)는 **구현 단계 실업로드로 확인**한다. 4MB 가 통과하지 못하면 상한을 더 낮추는 것이 개발자 재결정 사항이다.

**앱별 차이 (ledgercore 사전 확인 반영, 결정 #49)**
| 항목 | shipping | wholesale | ledgercore |
|---|---|---|---|
| 스토리지 쓰기 주체(현행) | 브라우저 직접 + `authenticated` INSERT 정책 | 서버 액션 | 서버 액션 + **사용자 세션 + RLS**(경로 첫 폴더=회사 id). **`service_role` Storage 쓰기 선례 없음** |
| 요청 본문 설정 | 없음(기본 1MB) | 8mb | 4.5mb |
| 버킷·정책 생성 | 마이그 | 마이그(206 등) | **마이그가 아니라 수동 SQL(개발자 승인) 선례** |
| 이 설계의 「`service_role` 전용·INSERT 정책 없음」 | 기존 관례(INSERT 정책)와 다름 | 대체로 맞음 | **관례와 다름** |
- **계약은 수단이 아니라 결과를 요구**한다(권장): ① 정식 경로에는 **서버 코드가 검사한 파일만** 저장 ② **메타 행이 없는 객체는 읽기 서명 URL 대상이 아님**(브라우저가 정책으로 직접 올린 미검증 파일이 있어도 열람·전달되지 않음) ③ 버킷 `file_size_limit`·`allowed_mime_types` 필수. 쓰기 주체가 `service_role` 인지 세션+RLS 인지는 **앱 관례에 맡긴다**. 단 세션+RLS 방식(ledgercore 관례)이면 `authenticated` INSERT 정책이 남아 서버 검사를 건너뛴 직접 쓰기가 가능하므로 ②·③ 가 유일한 방어가 된다 → 이 한계를 앱 문서에 적는다. `service_role` 로 가는 선택(§11-3 원안)은 방어는 더 강하나 ledgercore 에는 **새 패턴**이라 해당 담당·개발자 승인이 필요하다.
- **버킷은 게시판 전용으로 새로 만든다**(`board-attachments`). ledgercore 의 증빙 버킷은 불변·4MB·형식(PDF·이미지·xlsx·docx)이 다르므로 재사용·변경하지 않는다. 따라서 `txt·log` 허용과 `file_size_limit` 때문에 기존 증빙 버킷 설정을 바꿀 일은 없다(새 버킷에 처음부터 건다).
- **ledgercore 구현 절차**: 버킷·정책은 수동 SQL → 구현 단계에서 「수동 SQL 실행」을 개발자 승인 항목으로 명시하고, 스테이징 먼저. 마이그 파일에는 표만 둔다.
- **ledgercore 회사 삭제**: `platform_delete_tenant`(8060)는 스토리지를 건드리지 않고 `tenant_id` 표에 행이 남으면 삭제를 거부, 예약 삭제(8070)는 스토리지 정리 규칙이 아직 없다 [캡틴 전달]. 우리 결정 #26·#44 에 따라 게시판 표는 설정성으로 함께 지워지지만 **파일은 남는다** → 8070 설계 때 스토리지 접두(`<회사 id>/`) 삭제를 함께 정해야 한다(#44 의 구현 때 별도 승인 범위와 같음).

**버킷 제한과 시험 (wholesale 확인 반영)**
- 버킷에는 마이그에서 `file_size_limit`·`allowed_mime_types` 를 건다(선례: wholesale 마이그 206). **글당 5개 제한은 버킷으로 불가** → 서버 액션 + 표 제약(RPC 가 DB 에서 개수 재검사)으로 강제.
- **`.log` MIME 이 제각각**(`text/plain`, `application/octet-stream`, 빈 값 등)일 수 있다. 버킷 `allowed_mime_types` 에 `application/octet-stream` 을 넣으면 방어가 약해지고, 빼면 `.log` 업로드가 막힐 수 있다 → **실업로드 시험으로 브라우저별 MIME 을 확인**한 뒤 정한다. 서버 검사는 확장자 허용 목록 + 매직 바이트(이미지·PDF) / `txt·log` 는 「UTF-8 텍스트, 앞부분에 NUL 바이트 없음」으로 판정한다(텍스트는 매직 바이트가 없음).
- 위 시험(요청 한도·MIME·버킷 제한 거부 동작)은 **구현 승인 뒤 통합 시험 항목**으로 계약 문서에 적는다.

**계약에 넣을 규칙 (결정 #47)**
1. **플랫폼 운영자(`super_admin`·`PLATFORM_ADMIN` 등) 화면의 서버 코드는 1층 표를 `service_role` 로 읽지 않는다.** 스토리지 정책에 `super_admin` 을 넣지 않으면 세션 클라이언트에서는 닫혀 있지만 `service_role` 은 RLS·스토리지 정책을 우회하므로, `/admin` 서버 코드가 `service_role` 로 1층을 읽으면 「플랫폼 운영자는 승격된 2층만」 원칙이 깨진다. 플랫폼 운영자 경로는 **2층 전용 RPC·뷰(`board_escalations_v`)만** 호출한다.

3. 스토리지 정책에 `super_admin` 을 넣지 않는다(플랫폼 운영자는 서명 URL 발급 경로로만 2층 첨부를 본다).

## 12. 운영 스태프 셀프서비스 (2026-11-05 추가, 개발자 지시를 대장 캡틴이 전달 — 설계만, 구현 없음)

### 12-0. 원칙과 이 절의 지위
- **원칙(개발자 지시)**: 개발이 끝나면 개발자는 **프로그램 오류 수정과 신규 개발만** 한다. 업무 지원은 없다고 보고, 운영 스태프가 스스로 처리할 수 있어야 한다. 따라서 「바꿀 일이 생길 수 있는 값·동작」은 개발자의 SQL·환경변수·태그·코드 수정이 아니라 **스태프 화면 또는 스태프가 따라 하는 절차서**로 처리되게 설계한다.
- **이 절의 지위**: 새 결정 #50~#58(§12-10)이 확정되면 §6-3 최소안에 **포함**된다. 지난 조사(2026-11-05, 캡틴 보고)의 항목을 이 원칙으로 다시 정리한 것이다. 공용은 **상수·검증 함수·계약 문구**만, 화면·표·크론은 앱 몫(§1 경계 유지).
- **스태프 구분**: 테넌트 직원 = 대표·경리급(`hasEscalateRole`), 플랫폼 운영자 = 승격된 2층과 앱 전체 설정을 보는 계정(§9-1). 개발자는 스태프가 아니다.
- **★ 공통 규칙 문서 연동(2026-11-05)**: 사유(1~500자)·감사 형식·확인 단계 L1~L3·2인 승인·되돌리기의 **기준은 `ops-staff-screen-common-rules-2026-11.md`**(S-1 채택)이고, 아래 항목은 그 요약·게시판 적용이다. 충돌하면 그 문서가 우선. **B안: 위험 스위치(게시판 켜기 포함)의 2인 승인 장치는 1단계 제외·2단계로 미룸, 1단계는 이유+이름 입력 확인, 2단계는 오픈 전 필수.**
- **공통 규칙 (모든 스태프 변경 화면에 적용, 공용 계약 v1 에 포함)**
  1. 변경은 **서버 액션 → `service_role` 쓰기 RPC**(결정 #28 경로)만, RPC 가 `p_actor` 권한을 DB 에서 재검사.
  2. **감사 기록 필수**: 누가·언제·무엇을(설정 키 또는 글 id)·이전 값→새 값·사유. **글 본문·첨부 내용은 감사 기록에 남기지 않는다**(개인정보). 감사 표는 앱 기존 것을 쓴다(§1: shipping `admin_access_logs`, ledgercore `audit_log`/`platform_audit`, wholesale `audit_log`·`access_log`). 공용은 **감사 이벤트 코드값**(예 `BOARD_POST_REDACTED`, `BOARD_ATTACHMENT_DELETED`, `BOARD_SWITCH_ON`/`OFF`, `BOARD_SETTING_CHANGED`, `BOARD_RETENTION_RUN`)만 정한다.
  3. **허용 범위**: 숫자·문구 설정은 공용이 정한 `기본값 · 최솟값 · 최댓값`(또는 잠금 여부) 안에서만 저장된다. 범위 밖은 화면과 RPC 가 모두 거부(`SETTING_OUT_OF_RANGE`). 공용 순수 함수 `clampSetting`·`validateSetting` 으로 검사한다(시험 벡터 포함).
  4. 되돌릴 수 없는 동작(본문 지우기, 첨부 삭제)은 **사유 필수 + 확인 단계**를 둔다.

### 12-2. 글·첨부 개별 삭제 화면 (최소안 포함 제안, 결정 #50)
- **무슨 일**: 개인정보가 들어간 글·답글·첨부를 스태프가 직접 지운다. 기존 설계(§4-3 「본문 지우기」, §11-4·§11-5 「개별 첨부 삭제」)에 권한은 있으나 **화면이 최소안에 있는지는 앱 몫**이었다. 화면이 없으면 개발자 SQL 에 의존하므로 **화면을 최소안 필수로 올린다**.
- **화면**: 글 상세의 「본문 지우기」·첨부 줄의 「첨부 삭제」 버튼. 눌렀을 때 **사유 선택(개인정보 포함 / 부적절 / 법적 요청 / 기타+짧은 메모)** 필수, 확인 단계, 완료 뒤 글 자리에 `(삭제됨)` 과 삭제 시각·삭제 구분(작성자 본인이 아닌 스태프 삭제 등)만 표시.
- **권한**: 1층 = 해당 테넌트 대표·경리급. 2층 = 해당 테넌트 대표·경리급 + 플랫폼 운영자. 일반 운영자(staff)·일반 사용자는 불가(일반 사용자가 **자기 글을 지우는 것**은 별도 — 최소안에서는 안 둠, 스태프가 대신 처리).
- **본문과 첨부는 같은 흐름**: §11-5 순서 그대로 ① 메타에 삭제 표시 ② 파일 삭제 ③ 실패 시 정리 크론이 재시도. 글을 지우면 그 글의 첨부 전부가 같은 흐름에서 지워진다. 첨부만 지우는 것은 글 본문을 유지한다.
- **감사**: `BOARD_POST_REDACTED`·`BOARD_ATTACHMENT_DELETED` + 사유 코드. 본문은 남기지 않는다. 글 id·분류·상태·시각은 보존(§4-3 유일한 예외 원칙 그대로).
- **크기/위험**: M / 위험 높음(되돌릴 수 없음) → 사유·확인·감사로 완화. ledgercore 는 스토리지 삭제 절차(#44) 선행.
- **미확인**: 각 앱 설계서에 이 화면이 이미 있는지, 일반 사용자 자기 글 삭제 요구 여부.

### 12-3. 기능 스위치 + 법무 확인 체크 화면 (결정 #53)
- **무슨 일**: 게시판 글쓰기와 첨부를 **별도 스위치**로 켜고 끈다(§11-11 이미 별도 스위치 권장). 지금은 개발자가 마이그 뒤 승인받아 켠다(§10-3).
- **두 단계**: ① **앱 단위 스위치**(플랫폼 운영자) — 앱 전체 기능 노출. ② **테넌트 단위 스위치**(해당 테넌트 대표) — 자기 테넌트 사용 여부. 둘 다 켜져야 보인다. (권장. 대안: 플랫폼 운영자 한 단계만)
- **★ 승인 방식(2026-11-05 확정, 공통 규칙 문서 S-6·B안)**: 게시판 켜기는 「개인정보 스위치」로 보아 **2인 승인 대상**(끄기는 L1)이다. 단 **2인 승인 장치는 1단계에서 빼고 2단계로 미뤘다 — 1단계는 이유 + 대상 이름 입력 확인(L2)만**, 감사에 「2인 승인 미적용(1단계)」 표시. **2단계(2인 승인)는 오픈 전 필수 조건**. 근거 문서: `ops-staff-screen-common-rules-2026-11.md` §0-1.
- **켜기 조건(화면이 강제)**: 법무 확인 체크 — **법무 확인일(날짜)·확인자(이름)·확인 범위(보관 기간/처리방침/첨부 중 해당)** 를 입력해야 켜짐. 입력값은 감사에 저장(`BOARD_SWITCH_ON`). 법무 B-1~3(§10-1 B)을 체크 항목으로 화면에 나열.
- **끄기**: 언제든 가능. **기존 글·첨부는 보존**, 새 글쓰기·새 첨부만 막힘. 읽기·스태프 삭제·보관 정리 크론은 계속 동작(끄기가 보관 의무를 우회하지 않게). 끄기도 감사 기록.
- **저장 위치**: DB 설정 표(앱의 기존 기능 스위치 선례를 따름 — 선례 구현은 미확인). 환경변수 스위치는 쓰지 않는다(배포 필요 = 개발자 개입).
- **크기/위험**: S~M / 위험 중(법무 확인 전 켜기) → 체크 필수로 완화.

### 12-4. 작성 제한 수치 조정 (결정 #51: 저장 위치)
- **무슨 일**: 일반 사용자 하루 5건·분당 1건, 직원 하루 20건·분당 3건(결정 #19)과 첨부 일 총량(일 50MB) 등을 운영 중에 조정.
- **허용 범위(공용 상수, 제안값 — 확정은 #51 때)**:

| 설정 | 기본값 | 최솟값 | 최댓값 |
|---|---|---|---|
| 일반 사용자 하루 글 수 | 5 | 1 | 30 |
| 일반 사용자 분당 글 수 | 1 | 1 | 5 |
| 직원 하루 글 수 | 20 | 5 | 100 |
| 직원 분당 글 수 | 3 | 1 | 10 |
| 사용자별 일 첨부 총량(MB) | 50 | 10 | 100 |

- **값 저장 위치 — 결정안(권장 ㉯)**
  - ㉮ 코드 상수: 바꾸려면 배포 = 개발자 개입 → **원칙 위반**, 채택하지 않음.
  - **㉯ 앱 설정 표(테넌트별 행 또는 앱 전역 행) + 공용 상수는 기본값·허용 범위만(권장)**: 서버 액션이 설정 표에서 값을 읽고, **쓰기 RPC 가 DB 에서 범위를 다시 검사**. 값이 없으면 공용 기본값 사용.
  - ㉰ 환경변수: 배포 필요 → 채택하지 않음.
- **누가**: 테넌트 대표(자기 테넌트 값), 플랫폼 운영자(앱 전역 기본값). 감사 `BOARD_SETTING_CHANGED`(이전→새 값).
- **한계(원칙적으로 못 올리는 값)**: 첨부 개당 4MB·글당 5개·합계 15MB 는 **버킷·호스팅 한도에 묶여 있어 설정 화면 대상이 아님**(§12-7). 요청 본문 한도(호스팅)를 넘는 값은 설정으로 만들 수 없다.
- **크기/위험**: M / 위험 중 — 범위 제한으로 완화.

### 12-5. 안내 문구 변경 (결정 #52)
- **구조**: 문구마다 **id** 를 갖는다(예 `WRITE_NOTICE_PII`, `ATTACH_NOTICE_REDACT`, `PLATFORM_FORWARD_NOTICE`). 공용이 **기본 문구와 `locked` 여부**를 상수로 제공(결정 #5 공용 상수 유지).
- **덮어쓰기**: 앱(테넌트 단위 또는 앱 전역)이 설정 화면에서 문구를 덮어쓸 수 있다. 우선순위: 테넌트 덮어쓰기 → 앱 전역 덮어쓰기 → 공용 기본.
- **법무 필수 문구 잠금(`locked: true`)**: 개인정보 처리·플랫폼 전달 고지·첨부 가림 확인 등 법무가 확정한 문구는 **덮어쓰기 불가**(화면에서 읽기 전용, RPC 도 거부). 잠금 해제는 공용 상수 변경 = 신규 개발(태그).
- **문구 검증**: 덮어쓰는 문구는 길이 제한과 필수 단어(예 「개인정보」) 포함을 `validateOverride` 로 검사해 필수 고지가 약해지지 않게 한다. 제한은 계약 문서에 적는다.
- **감사**: `BOARD_SETTING_CHANGED`(문구 id, 이전→새 문구 해시 또는 앞 80자). 변경 이력 화면에서 되돌리기 가능(이전 값 복원).
- **크기/위험**: M / 위험 중(필수 고지 약화) → 잠금과 검증으로 완화.

### 12-6. 분류 추가 · 보관 정리 · 첨부 정리 · 알림 수신
**(가) 1층 분류 추가 (결정 #54)**
- 결정 #7 의 「앱이 추가할 수 있게 열어 둠」을 스태프가 하려면, 분류를 **DB CHECK 가 아니라 분류 표 참조**로 바꿔야 한다(CHECK 변경은 마이그 = 개발자). **공용 코드값 3개(공지·문의·인수인계)와 2층 코드값은 고정**, 앱·테넌트 추가분만 표에 둔다.
- 화면: 테넌트 대표가 분류 이름·사용 여부를 추가/숨김(삭제는 안 함, 기존 글 보존). 감사 기록. 일반 사용자 작성 가능 분류(`QUESTION`·`SUGGESTION`, #21)는 스태프가 바꾸지 못하게 고정.
- **계약 v1 모양에 영향**(코드값 목록 + 앱 확장 규칙) → 태그 전에 결정해야 한다. 크기 M / 위험 낮음.

**(나) 보관 정리 확인과 수동 실행 (결정 #55)**
- 화면(플랫폼 운영자): 마지막 정리 실행 시각·삭제 건수·실패 건수, 다음 예정, **수동 실행 버튼**(감사 `BOARD_RETENTION_RUN`). 크론이 며칠 안 돌았으면 화면에 경고.
- **보관 기간 값의 변경 권한**: 법무 확정값이 최솟값(더 짧게는 법무 확인 후)이므로 **화면에서는 법무 확정 기간 이상으로만** 늘릴 수 있고 줄일 수 없게 한다(권장). 줄이려면 법무 확인 뒤 신규 개발(마이그).
- 크기 M / 위험 높음(개인정보 삭제 시점) → 수동 실행도 사유 입력과 감사.

**(다) 첨부 정리**
- 화면(플랫폼 운영자): 테넌트별 첨부 건수·용량, **메타 없는 객체(고아) 수**, 정리 버튼(감사). 고아 정리는 **자동 크론(주 1회)** 이 기본이고 화면은 확인과 수동 실행용.
- 테넌트 해지 시 접두 삭제는 해지 절차에 포함(§11-5). ledgercore 는 스토리지 삭제 절차 선행(#44).
- 크기 L / 위험 높음(ledgercore 는 새 패턴).

**(라) 알림 수신 설정 (결정 #56)**
- 화면: 테넌트 대표가 새 글 알림 수신자(대표·경리 기본, #29)를 켜기/끄기. 플랫폼 운영자는 2층 새 글 알림의 수신 수단(앱 알림 기반이 있는 곳만)과 수신자 목록. 마지막 발송 기록 표시.
- 알림 기반이 없는 앱(ledgercore)은 배지만. 클라우드 감시자(결정 #4)로 가는 알림의 수신자는 **오픈 준비 때 개발자가 아닌 운영 담당이 정하도록** 절차서에 넣는다(§12-8).
- 크기 M / 위험 낮음. 미확인: 앱별 알림 기반.

### 12-7. 화면 비권장이던 것 → 절차서·자동화 대안
화면으로 만들지 않는 이유는 모두 「비밀값이거나 인프라 값이라, 화면에 두면 오히려 위험」이다. 대신 **스태프가 따라 하는 절차서**와 **자동화**로 개발자 개입을 없앤다. 절차서는 오픈 전에 개발자가 쓰고(§12-8), 이후 스태프가 갱신한다.

| 작업 | 왜 화면이 아닌가 | 스태프용 절차서(요지) | 자동화 대안 |
|---|---|---|---|
| 비밀 키 회전(`secrets` 키링) | 키가 화면·로그에 노출되면 사고 | ① 호스팅 환경변수 화면에서 새 키를 현재, 옛 키를 `_PREVIOUS` 로 ② 재배포 ③ 앱의 「재암호화 실행」 관리 화면(또는 정해진 절차) ④ 남은 구키 행 0건 확인 ⑤ `_PREVIOUS` 제거. 각 단계 확인 화면 캡처 | **회전 주기 알림**(예 연 1회)과 「구키 행 남은 건수」 확인 쿼리를 크론/관리 화면으로 제공. 재암호화는 `needsRewrite` 행을 읽을 때 자동 재기록하는 방식 권장(키링 설계에 있음) |
| 결제 키·웹훅 비밀 교체, 테스트→라이브 전환(`expectedMode`) | 결제 비밀 | 호스팅 환경변수 교체 → 재배포 → **스테이징 선행** → 시험 결제 1건 확인 → 운영 반영 | 키 종류 불일치(`expectedMode`)는 라이브러리가 이미 거부하므로 **헬스 체크 화면**(키 종류·모드 표시, 값은 비표시)을 앱이 제공하도록 권장 |
| FCM 키 교체 | 푸시 비밀 | 호스팅 환경변수 교체 → 재배포 → 시험 푸시 1건 | 발송 실패율 알림 |
| 첨부 버킷 한도(개당 4MB 등) 변경 | 인프라·호스팅 한도와 묶임, 임의 상향 불가 | **스태프가 바꾸지 않는다.** 한도를 바꿔야 하면 「한도 변경 요청서」 양식으로 신규 개발 요청(호스팅 본문 한도·요금제 확인 포함) | 용량 80% 도달 시 알림(§12-6 다) |

- 원칙: 이 표의 작업은 **비밀값을 스태프가 직접 다루기 어렵거나, 잘못하면 서비스가 멈춘다**. 그래서 ① 절차서 ② 스테이징 먼저 ③ 확인 쿼리/헬스 체크 화면 ④ 알림 으로 감싸고, 정말 막히면 「오류 수정」으로 개발자에게 올리는 경로를 절차서에 적는다. 이 작업을 **누가(운영 담당) 수행하는지는 개발자 결정이 아니라 운영 조직의 결정**이며 본 문서가 정하지 않는다(결정 #58 에서 지정 요청).

### 12-8. 오픈 때 개발자가 마지막으로 해 두는 일 (인수 체크리스트 제안)
개발이 끝나고 업무 지원이 없다는 전제이므로, **오픈(운영 반영) 전에 한 번에** 해 두고 이후엔 손대지 않는다.
1. 앱 단위·테넌트 단위 스위치 초기값 설정과 **법무 확인 이후 켜는 절차 확인**(켜기 화면 시험 포함).
2. 허용 범위·기본값 확정(§12-4)과 법무 필수 문구 `locked` 확정(§12-5), 법무 확정 보관 기간 입력.
3. 정리 크론(보관 정리, 첨부 고아 정리, 삭제 재시도)이 **운영에서 돌고 있고 실패 알림이 수신자에게 간다**는 확인. 호스팅 크론 한도 확인.
4. 버킷 `file_size_limit`·`allowed_mime_types` 와 호스팅 본문 한도 **4MB 실업로드 통과 확인**(§11-13 C), Supabase 요금제 용량 알림 설정.
5. 알림 수신자·알림 수단 초기 설정, 클라우드 감시자 수신자 지정(운영 담당).
6. **절차서 4종 작성·시험**(키 회전, 결제 키 교체, FCM 키 교체, 한도 변경 요청)을 스테이징에서 스태프가 실제로 한 번 따라 해 본다.
7. 플랫폼 운영자·테넌트 대표 계정과 권한 확인(ledgercore 장터 회사·`PLATFORM_CONSOLE` 켜기 승인 포함, #13).
8. 감사 기록이 쌓이고 화면에서 조회되는지 확인(변경 이력 화면).
9. 헬스 체크 화면(키 종류·모드, 크론 마지막 실행, 용량) 확인.
10. 인수 문서: 이 설계서·계약 문서·절차서·화면별 권한표를 운영 담당에게 인계.

- §1 경계 유지: 화면·표·크론·절차서는 앱 몫, 공용은 상수·검증·계약.

**미확인 (읽지 못함)**
- 각 앱의 기존 설정 화면 형태, 감사 표 열 구조, 기존 기능 스위치 저장 방식(DB 열인지 env 인지).
- 크론 실행 방식(Vercel Cron·Supabase)과 실패 알림 기반, 앱별 알림 기반.
