# ai-guard 개인정보 가림 누락률 측정 (2026-11-28)

- 대상: `src/ai-guard` (규칙 `ai-guard-rules/3`), 기본 정책 + 차량번호(PLATE) MASK. STANDARD·STRICT 둘 다 측정.
- 예문: 가짜 예문 **444건**(개인정보 칸 414개, 개인정보 아닌 미끼 칸 258개). 고정 시드라 다시 돌려도 같다. 실제 개인정보 없음(형식만 맞춘 난수, 이메일은 예약 도메인).
  - 종류별 단독 324건(9종 × 36), 3~4종 섞인 접수·메모 문장 30건, 개인정보 없는 문장 90건.
  - 변형: 하이픈·띄어쓰기·붙여쓰기·점·전각 숫자·유니코드 대시·구분자 양옆 공백, 한자·영문 이름, 한자·영문 단서어(連絡處·Tel.·Biz No.), 문장 속에 묻힌 경우.
  - 미끼: 금액·주문번호·송장번호·날짜·일시·수량·바코드·대표번호·우편번호·업무 낱말.
- 재현: `npx vitest run --config scripts/ai-guard-measure/vitest.measure.config.ts` → `scripts/ai-guard-measure/result-shared.md`(전체 표). 외부 호출 없음, 평소 `npm test` 에 들어가지 않음.
- 판정: 개인정보 칸의 글자(문자·숫자)가 전부 토큰으로 덮이면 «가림», 일부만이면 «부분 노출», 전혀 안 덮이면 «누락». 누락률 = (누락+부분)/표본. 미끼 칸은 한 글자라도 덮이면 «오탐».
- 한계: 예문 분포는 사람이 정한 변형을 고르게 돌린 것이라 **실제 입력 분포의 누락률이 아니다**(변형별 취약점 지도로 읽을 것). 일부 문맥(예: «인수자(引受者) 이름»)은 일부러 까다롭게 만들었다.

## 3. 고칠 후보 (안만 — 이번에 ai-guard 동작은 바꾸지 않았다)

1. **숫자 구분자 정규화 확대**(누락 57건 → 대부분 해소 예상): 탐지용 사본에서 숫자 사이 ` - `·`.`·공백 구분을 `-` 로 합친 뒤 기존 감지기 적용. 주의: 소수(`12.5`)·점 날짜(`2026.11.28`)는 기존 ISO 날짜·소수 예외로 빠지는지 시험 필요. 공백 묶음 계좌는 오탐(수량 나열 등) 증가 위험이 있어 «3묶음 이상·합계 10~14자리»로 좁힌다.
2. **주소 감지기 공용화**(누락 46건): 앱 자체 구현에 있는 주소 감지기를 쉐어드로 올리고 경계를 넓힌다(시·도부터 동·호수까지). 지금 쉐어드는 경고 건수만 센다.
3. **이메일 우회 표기 + 오탐 줄이기용 문맥 단서**: 이메일 변형 26건 해소. 오탐 쪽은 «송장·운송장·주문·접수·발주·바코드» 단서어가 바로 앞에 있으면 연속 숫자를 계좌로 보지 않는 예외(송장·주문번호 오탐 44건 중 대부분 해소). 단서 없는 10~16자리는 지금처럼 가린다(안전 쪽).

모델이 필요해 보이는 것: 단서 없는 문장 속 이름(한글), 한자·영문 이름 일반, 주소 경계 판단, 단서 없이 숫자 성격(계좌 vs 주문번호) 구분. 이름이 누락 상위이므로 2단계 소형 모델 검사는 **이름·주소 두 종류에만 좁혀** 검토하는 것이 비용 대비 효과가 크다(번호류는 위 규칙 보강으로 충분).
